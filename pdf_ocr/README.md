# PDF文字認識 — 画像PDFを選択・検索できるPDFにする

スキャンした PDF や、画像から作った PDF は、見た目は文字でも中身は「絵」なので、選択もコピーも検索もできません。このツールは OCR で読み取った文字を、**写っている文字の上に「見えない文字」として重ねます**。見た目は元のまま、Ctrl+F で検索でき、マウスで選択してコピーできる PDF になります。

Windows で、PDF をバッチファイルにドラッグ＆ドロップするだけで使えます。

## できること

- 画像だけの PDF → テキスト選択・検索ができる PDF（元の名前 `_OCR.pdf`）
- 横書き・縦書きの日本語、図面のように文字が散らばったもの、英数字中心の資料
- 横倒し・上下逆のページは、自動で向きを直してから読み取る
- フォルダごと・複数ファイルまとめて変換
- すでに文字が入っているページは素通し（二重に重ねない）
- 元のページはそのまま残すので**画質は変わらない**

## 準備（初回だけ）

1. **Python** … https://www.python.org/downloads/windows/
   インストール画面の「Add python.exe to PATH」に必ずチェックを入れる
2. **Tesseract OCR** … https://github.com/UB-Mannheim/tesseract/wiki
   ページにある `tesseract-ocr-w64-setup-5.x.x.xxxxxxxx.exe` をダウンロードして実行し、ウィザードの **Choose Components** の画面で `Additional language data (download)` を [+] で開いて **Japanese** と **Japanese (vertical)** にチェック。
   インストール先は既定の `C:\Program Files\Tesseract-OCR` のままでよく、PATH の設定も不要です（その場所を自動で探します）。
   **チェックを忘れても構いません** — 足りない言語データはツール側で用意します（下記）。
3. リポジトリ直下の [`pdf_ocr.zip`](../pdf_ocr.zip)（＝`dist/` の中身）を好きな場所に展開し、**`PDF文字認識.bat` をダブルクリック**する
   準備ができていなければ、番号を選ばせずにそのまま準備が始まります（`pypdfium2` `pypdf` `reportlab` `pillow` と言語データが入り、最後に環境を確認）。

## 使い方

**利用者が触るファイルは `PDF文字認識.bat` の 1 本だけです。**

| 操作 | 起きること |
|---|---|
| PDF（またはフォルダ）をドラッグ＆ドロップ | そのまま変換する |
| ダブルクリック（準備がまだ） | そのまま準備する |
| ダブルクリック（準備ずみ） | 「閉じてよい」と伝え、変換するファイルだけを聞く |

### 番号のメニューを既定から外した経緯

はじめは、ダブルクリックで `[1]〜[7]` の一覧を出して選ばせていました。実際に使ってもらうと、同じ人が続けて 3 回つまずきました。

1. `[1] 初回の準備をする` を実行してほしいと伝えたところ、**「番号を入れて Enter と出ますが」** — 画面の `[1]` をそのまま打つのか、数字だけなのかが分からない
2. `[1]` と打つと無言で画面を描き直していたため、**同じ画面が出続けるだけ**に見える
3. 表示を直したあとも **「結局、0〜7 番を順番に全部打ち込むという事ですか」** — 一覧は「選ぶもの」ではなく「順に実行する手順」に見える
4. さらに直したあとも **「いくつも選択肢があるのですか」**

原因は表現ではなく構造でした。**やることが 1 つしかない場面で選択肢を出していた**のが誤りです。3 段階で外しました。

- **準備がまだなら、何も聞かずに準備する。** `--selftest --no-download` で状態を見て、できていなければそのまま実行する
- **準備がすんでいるなら、まず「この画面は閉じてかまいません」と伝える。** ふだんの使い方はドラッグ＆ドロップだけなので、この画面自体に用がない
- **それでも聞くのは 1 つだけ。** 変換したいファイルの場所。空の Enter で閉じ、`m` でだけ従来の一覧に入る

調べる・入れ直すといった操作は消していません。既定の道から外し、`m` の先に置いただけです。**選択肢の数を減らすのではなく、選択させる場面を減らす**のが要点でした。

読み取り方は**自動で決まります**（`--mode auto`）。横書きの申請書でも、縦書きの書籍でも、図面でも、同じように落とせます。

配布物は次のとおりです。

```
PDF文字認識.bat        これを使う
PDF文字認識_GUI.pyw    画面（GUI）で操作する版。エンジンを選べる
使い方.txt             利用者向けの説明
設定.ini               細かい調整（ふつうは触らない）
pdf_ocr.py             本体
ppocr_onnx.py          PP-OCRv5（ONNX 版）の検出・認識
models/                PP-OCRv5 mobile の模型（同梱）と文字の辞書
サンプル.pdf           動作確認用
```

### 画面（GUI）で操作する

`PDF文字認識.bat` のメニュー `[8]`、または `PDF文字認識_GUI.pyw` を直接ダブルクリックすると、画面で操作できます。

- 横書き・縦書きそれぞれの読み取りエンジンを、`tesseract`（既定・精度重視）・`tesseract`（速度重視・`tessdata_fast`）・`PP-OCRv5 mobile`・`PP-OCRv5 server` から選べる
- 選んだエンジンは次回も覚えている
- PDF（複数・フォルダも）を画面にドラッグ＆ドロップすると、そのまま変換が始まる。ドラッグ＆ドロップが使えない環境では「PDF を選ぶ…」ボタンに切り替わる
- ページごとの進み具合を進捗バーとログに表示する
- 変換の途中でキャンセルできる（そこまで読めたページで打ち切って保存する）
- `PP-OCRv5 server` を選び、模型がまだ無いときは、165 MB を取得してよいか確認してから取得する（「いいえ」なら、その変換は `tesseract` で読む）
- ファイルごとの所要秒数を、`%LOCALAPPDATA%\pdf_ocr\変換ログ.csv`（設定ファイルと同じ場所）に追記していく。画面のログ欄は閉じると消えるが、こちらは残るので、エンジンの組み合わせによる速さの違いをあとから比べられる。起動時に画面のログへ実際の置き場所を表示する

エンジンを選べるのはこの画面からだけです。`PDF文字認識.bat` は今までどおり `tesseract` だけで読みます（読み取り方そのものは自動判定のままで、変わりません）。

### なぜ 1 本にまとめたか

もとは読み取り方ごとに `PDF文字認識_縦書き.bat` `_縦横混在.bat` `_図面.bat` `_英数字.bat` … と 12 本の bat を置き、利用者に選ばせていました。これは誤りでした。

- **利用者は資料の種類を分類したいのではなく、選択できる PDF が欲しいだけです。** 「縦書きが少しでも混ざっていれば縦横混在」という判断を毎回させるのは、こちらの都合を押し付けています
- 選択を誤ると静かに品質が落ちます。縦書きのある資料に横書き用の bat を使うと、縦組みを丸ごと取りこぼしますが、画面には何も出ません
- ファイルが並んでいるだけで、どれが本命か分からなくなります

`auto` は、**判断をこちら側に寄せた**ものです。

1. 横書きとして読み、縦書きでもう一度読んで、縦組みに読めた所だけ差し替える（＝従来の `mixed`）
2. それで取れた文字列が `SPARSEUNDER`（既定 12）個に満たないページだけ、散在向けの `SPARSEPSM`（既定 11）でもう一度読み、多いほうを採る（＝従来の `zumen` への備え）

2 は文章のページでは起きないので、実測で `mixed` と同じ速さです（同梱サンプルで 5.9 秒 → 5.6 秒）。図面のページでは専用モードと同じ結果になりました（散らばった 7 語のうち 6 語。横書き専用モードでは 2 語）。

横書きだけの資料ばかりで速さを優先したいときは、`設定.ini` の `[settings]` に `MODE=yoko` と書けば従来どおり片道で読みます（実測 5.6 秒 → 2.5 秒）。**既定を速さではなく確実さに置いた**のが今回の変更です。

## 仕組み

```
入力PDF ──① pypdfium2 でページを画像に描画（既定 300dpi・貼られた画像が細かければそこまで上げる）
        ──② tesseract で OCR（TSV で単語ごとの位置を受け取る）
        ──③ reportlab で「見えない文字」だけのページを組み立てる
        ──④ pypdf で元のページに重ねて保存
```

ポイントは③で、`Tr 3`（描画しないテキスト表示モード）で文字を置きます。ビューアには表示されませんが、検索・選択・コピーの対象にはなります。文字の大きさは枠の高さ、横方向の伸縮率は `100 × 枠の幅 ÷ 文字列の幅` で決めるので、選択したときの反転範囲が実際の文字とほぼ重なります。

フォントは Windows の MS ゴシックなどを**実体ごと埋め込む**（サブセット）ため、`ToUnicode` が付いてどのビューアからでも日本語を取り出せます。見つからない環境では埋め込みなしの CID フォント（HeiseiKakuGo-W5）で代用します。

### 行としてつなぐ

tesseract は 1 行を単語ごとに区切って返します（日本語では「現場」「名」「第」「二」「駐車場」…のように細かく割れる）。これを単語ごとに別々の文字列として置くと、単語ごとに文字の大きさとベースラインが少しずつ違うため、ビューアが「別の行」と判断します。すると選択してコピーしたときに `建築` と `物省エネ法（概要）` のように分断され、通しでは検索もできません。

そこで TSV の `block_num` / `par_num` / `line_num` で同じ行の単語をまとめ、1 本の文字列として置いています。日本語どうしの境目は詰め（詰めないと通しで検索できない）、英数字どうしで間隔が空いていれば空白を入れます。表の別の欄まで繋げてしまわないよう、文字の高さの 1.5 倍より広く空いたところでは切ります。

縦書きかどうかは単語単位ではなく**行の外形**で判定します。1 文字ずつ見ると正方形に近く、判断できないためです。

### 足りない言語データを自分で用意する

Tesseract のインストーラは日本語データが既定で外れており、`Japanese (vertical)` に至ってはさらに見落としやすい場所にあります。入っていなければ縦書きは読めません。そこで、必要な `.traineddata` が無いときは公式の配布リポジトリ（Apache-2.0）から取得します。

置き場所は 2 段構えです。Tesseract 本体の `tessdata` フォルダに書き込めればそこへ、書き込めなければ（`C:\Program Files` 配下で権限が無い場合など）ツール自身のフォルダに `tessdata` を作ってそこへ置き、以降の呼び出しに `--tessdata-dir` を渡します。Tesseract は言語データの置き場を 1 つしか見ないため、後者のときは既存の `jpn` / `eng` / `osd` もそこへ複製します。

取得先は `raw.githubusercontent.com` と `github.com/…/raw/…` の 2 つを順に試します（社内ネットワークによってどちらか一方しか通らないことがあるため）。どちらも駄目なときは、**足りないファイル名・その直リンク・置き先フォルダの絶対パス**を並べた案内を出します（`tessdata` には 100 以上のファイルがあるので、名指ししないと選べないため）。`--no-download` で取りに行かない動作にもできます。

日本語の資料に要るのは次の 4 つだけです。

| ファイル | 用途 | 大きさ |
|---|---|---|
| `jpn.traineddata` | 横書きの日本語 | 約 34 MB |
| `jpn_vert.traineddata` | 縦書きの日本語 | 約 3 MB |
| `eng.traineddata` | 英数字 | 約 22 MB |
| `osd.traineddata` | ページの向きの自動判定 | 約 10 MB |

`PDF文字認識.bat` のメニュー `[1] 初回の準備をする`（`--install-langs`）で、`jpn` / `jpn_vert` / `eng` / `osd` をまとめて用意します。

### 言語データの版を上げる（いちばん効いた）

**このツールで最も精度を動かしたのは、処理の工夫ではなく言語データの版でした。**

tesseract の日本語データには 3 つの版があります。

| 版 | jpn の大きさ | 位置づけ |
|---|---|---|
| tessdata_fast | 2.4 MB | 速いかわりに精度が落ちる |
| tessdata（標準） | 35.7 MB | 精度重視。このツールが取ってくる版 |
| tessdata_best | 14.3 MB | 最高精度。いちばん遅い |

**Windows のインストーラ（UB-Mannheim）が入れるのは速度優先版です。** このツールは足りない言語データを標準版から取ってきますが、インストーラが既に置いていると「足りている」と判断して触りませんでした。結果として、利用者はずっと速度優先版で読んでいたことになります。

実際の紙面（横組み二段の見開き）で、狙った 16 語のうち取り出せた数。

| 言語データ | 取り出せた数 |
|---|---|
| 速度優先版 | 9/16 |
| 標準版 | **15/16** |
| 最高精度版 | 13/16 |

速度優先版でだけ落ちていたもの。**どれも、こちら側の直し方をいくら変えても届かなかった誤りです。**

| 正しくは | 速度優先版 | 標準版 |
|---|---|---|
| 経験と勘で | 経験とで | ○ |
| 震災による倒壊 | による倒壊 / 震炎による倒壊 | ○ |
| ぜひともご活用 | ぜひとるもご活用 | ○ |
| 構造検討や構造計算 | 構造検討構造計算 | ○ |
| 比較できるよう、記載 | 比較できるよう、**mult**記載 | ○ |
| 2024年10月 | （丸ごと消える） | ○ |

#### ただし、常に勝つわけではない

**精度重視版は横組みで強く、縦組みで弱い。** 同じ 4 つの紙面を両方の版で読んで、狙った語を数えたもの。

| 紙面 | 精度重視版 | 速度優先版 | 勝ち |
|---|---|---|---|
| 横組み二段（実物） | 信頼度 94.1 → **15/16** | 92.8 → 9/16 | 精度重視 |
| 縦組み（実物） | 79.1 → 12/16 | 89.5 → **15/16** | 速度優先 |
| 表（縦組みの見出し入り） | 56.9 → **まるごと化ける** | 93.6 → 正しい | 速度優先 |
| 縦組み（合成） | 85.0 → 12/16 | 94.6 → 正しい | 速度優先 |

3 行目がいちばん極端で、精度重視版は紙面全体を縦組みと誤判定し、`建築物省エネ法（概要）` が `縄 郊 でい 塞 盛…` になりました。**単純に置き換えると、いま読めている資料を壊します。**

そこで **両方を残し、ページごとに選びます**。

- 精度重視版はツールの隣の `tessdata` フォルダへ入れ、**tesseract 本体の置き場は書き換えません**。元の版を残しておかないと、戻る先がなくなるためです。
- ページを読んだ結果の平均信頼度（字数で重み付け）が 90 以上なら、そのまま採ります。
- 90 未満のときだけ、元の版でも読み直して、信頼度の高いほうを採ります。

上の 4 例では、**平均信頼度の高いほうが 4 例とも正しい**ほうでした。しきい値を 90 にすると、いちばん重い横組みのページ（94.1）だけが二度読みを免れ、残り 3 例は読み直して正しいほうに変わります。精度重視版は 2 倍以上遅い（同じ紙面で 77 秒 対 34 秒）ので、この線引きが要ります。

#### 運ぶのは言語データだけでは足りない

`--tessdata-dir` を指定すると、tesseract は言語データだけでなく**出力形式の設定ファイルもそのフォルダから探します**。このツールは `tsv` を使うので、`configs/tsv` が無いとそれを**黙って無視し**、表ではなくただの文章を返します。すると読み取り位置が 1 つも取れず、**変換しても文字が 1 つも入らない PDF ができます**。エラーにならないので気づきにくい。言語データを移すときは `configs` も一緒に運びます。

同じ理由で、**次の起動でそのフォルダを見つけられるようにしておくこと**も要ります。見落とすと、本体の置き場に残った速度優先版だけを見て「まだ速度優先版だ」と判断し、起動のたびに 50 MB 以上を取り直します。

取得が途中で切れたときは、**半端なファイルを残しません**。届いたものが速度優先版の大きさ未満なら壊れたと見なして消し、元の版の複製をそのフォルダに置いて、そのまま続けます。

見分けは大きさで足ります（日本語 2.4 MB 対 35.7 MB と桁が違う）。縦書き用の `jpn_vert` は速度優先版と標準版がほぼ同じ大きさ（3.0 MB）なので、見分けず、置き換えもしません。

#### いまは取得ではなく同梱

上のくだりはネットワークから取ってくる前提で書きましたが、**いまは配布物に `tessdata/jpn.traineddata`（精度重視版、`tessdata_best`）を同梱しています**。社内ネットワークから取りに行けない環境でも確実に効かせるためです。取得はここに同梱が無いときの逃げ道として残してあります。

同梱に切り替えたことで、置き場の決め方も変わりました。**tesseract 本体には手を触れず**、以下の場所を順に試して、実際に使えたものを採ります。

1. `pdf_ocr.py` の隣の `tessdata` フォルダ
2. `%LOCALAPPDATA%\pdf_ocr\tessdata`（無ければ `%ProgramData%` → `%APPDATA%` → ホームフォルダの順）
3. 一時フォルダ

「使えた」は、ファイルがそろっているかだけでは判定しません。**実際に tesseract へ小さな画像を読ませてみて、通るかどうかで決めます。** ファイルがあることと tesseract がそこを開けることは別で、Windows では道筋に日本語が入っていると開けないことがあります。配布物のフォルダ名は「PDF文字認識」なので、1 つ目の候補がまさにこれに当たり得ます。開けないまま進むと、変換しても文字が 1 つも入らない PDF ができ、エラーにもならないので気づけません。

さらに、フォルダの中身を数えるのに **tesseract には聞きません。** ファイル名をこちらで数えるだけにしています。以前は `tesseract --list-langs` の答えで数えていましたが、その問い合わせ自体が失敗すると「1 つも入っていない」と読み違え、**正しく同梱をそろえてあるのに**

```
言語データをそろえられませんでした（eng, jpn, jpn_vert, osd）。
速度優先版のまま読みます（精度が落ちます）。
```

と出て、速度優先版のまま読み進めていました。実際に利用者の環境で、以前のフォルダを消して同梱ごと最新の配布物に入れ替えても、この表示が出ました。tesseract がエラーを 1 行だけ返すと、その 1 行を見出しとして読み飛ばす作りだったため、結果が空になっていたのが原因です。ファイルの有無はこちらのファイルシステムの話なので、tesseract に聞かず自分で数えれば、この読み違いは起きません。

`tools/selfcheck.py` の「言語データ」の項目が回帰テストです。tesseract を一切呼ばずに、この一連の判断（数える・開けない置き場を飛ばす・相対の道筋を作らない・どちらの版か毎回出す）を確かめます。

#### なぜここに行き着くのが遅れたか

開発環境の `jpn.traineddata` が apt で入った 2019 年のもので、**その中身が tessdata_fast そのものでした**（MD5 一致）。つまり手元での測定はすべて速度優先版でのもので、「直したのに変わらない」の一因は、こちらの測定環境が利用環境の悪いほうと同じだったことです。

版を上げると、それまで見えていなかった誤りが 2 つ出てきました。どちらも取りこぼしではなく、**字の種類だけを一貫して間違える**もので、後段で直せます。

- 年月の数字が丸数字になる。`2025年4月` → `②0②⑤年④月`、`2024年10月` → `⑳②④年①0月`。形は正しいので、丸数字を数字に直します。ただし紙面の箇条書き `①構造の本を読んでも理解できない` を数字にしてはいけないので、**ふつうの数字と地続きに並んでいるか、すぐ後ろが年月日のときだけ**直します。
- 開きのかぎかっこが ``` ` ``` になる。実際の紙面では **17 個すべてがこれ**で、閉じの `」` は 17 個とも正しく、正しい `「` は 1 つもありませんでした。すぐ後ろが漢字・かなのときだけ `「` に直します（コードを載せた資料のバッククォートは触りません）。

### 信頼度 0 で返ってきた正しい字を、捨てないようにする

言語データの版を上げたあとも、利用者の資料では字が消え続けていました。**消していたのは tesseract ではなく、こちらの足切りでした。**

利用者の資料（`はじめに` のページ）を 500dpi で読ませ、素の tesseract の出力と、こちらの変換結果を突き合わせた実測です。

| 正しい語 | 素の tesseract | 変換後 | 消えた字の信頼度 |
|---|---|---|---|
| 構造塾 | ○ | 「構造」をご活用ください | 0.0 |
| 地盤補強工事業者 | ○ | 地補強工事業者 | 0.0 |
| 震災による被害 | ○ | 災による被害 | 0.0 |
| 言葉、数値が難しい | ○ | 言葉が難しい | 0.0 |
| 2024年10月 | ○ | 2024 月 | — |

`MINCONF`（既定 30）未満の語を捨てていたのが原因です。捨てた 12 語を並べてみると、**12 語すべてが正しい字**でした。

これは誤読より始末が悪い症状です。字が化けていれば見て気付けますが、**消えた字は前後とつながって、読める別の語になる**ので気付けません。`地盤補強` が `地補強` になっても、読み流せてしまいます。

かといって足切りをやめると、別の害が出ます。同じ資料の縦組みのページ（図が半分を占める見開き）では、足切りで捨てていた 104 語の大半が**罫線を `本` と読み違えたもの**で、同じ場所に 24 個続いていました。

そこで、**行として見て**分けます。実測すると、両者ははっきり分かれていました。

| | その行の、自信のある字の平均信頼度 |
|---|---|
| 本文の行（穴が空いている） | 81〜95 |
| 図の領域のごみの行 | 44〜72 |

`keep_holes()` は、次の 4 つをすべて満たす字だけを拾い直します。

1. その行の、自信のある字の平均信頼度が 80 以上
2. その行に、自信のある語が 2 つ以上ある
3. 拾う字が、その行の自信のある字に**前後を挟まれている**
4. 拾う字が、その行の幅からはみ出していない

3 が要点です。**ごみは行の端に出るか、行ごとごみになります。挟まれた穴は本文にしか空きません。** 4 が無いと、列の横に離れた字まで拾って行の枠が広がり、読む順が変わりました（実際に、縦組みのページで 1 行が末尾へ飛びました）。

利用者の実物 2 つと、以前からの実物 2 つで測った結果です（正解語 16 個ずつ）。

| 資料 | 拾い直しなし | 拾い直しあり |
|---|---|---|
| 縦組みの見開き（今回） | 9/16 | 12/16 |
| 横組みの `はじめに`（今回） | 8/16 | 14/16 |
| 横組みの `はじめに`（以前） | 12/16 | 14/16 |
| 縦組みの本（以前） | 8/16 | 11/16 |
| 合計 | 37/64 | **51/64** |

4 つとも良くなり、悪くなったものはありません。

数字を散らして拾う `sparse_numbers()` では切ってあります（PSM 11 は行の並びを推測しないので、行を手掛かりにする判断が成り立たない）。

#### 代償：空白だった所に、誤った字が出るようになる

拾い直した字が誤っていれば、**以前は空白だった所に誤った字が出ます。** 利用者の資料で実際に起きました。

| 版 | その箇所 |
|---|---|
| 入れる前 | `[新耐基準|` ← `震` が消えている |
| 入れた後 | `[新耐謀基準|` ← 字は入ったが誤り |

その場所だけを切り出すと 200〜600dpi のどの解像度・どの読ませ方でも `新耐震基準` と正しく読めます。**画像は綺麗で、紙面全体で読ませたときだけ縦書きパスが `謀` を信頼度 0.0〜0.9 で返します。**

実際に拾い直された字（tesseract 5.5.3、実物 2 つ）。

| 資料 | 字数 | 中身 |
|---|---|---|
| 横組みの `はじめに` | 8 | **8 字すべて正しい**（震・、・①・、・数値・塾・盤・木造） |
| 縦組みの見開き（図が半分） | 10 | 正しいもの（耐震・と）と、ごみ（`有`・`bi`・`自`・`ハ`）が混在 |

**信頼度で切り分けることはできません。** 正しく拾えた `塾`・`盤`・`震` はすべて信頼度 **0.0** で、誤った `謀` も 0.0 です。下限を 0 より上げれば、誤りと一緒に正解も失います。

全体では 37/64 が 51/64 になったので、この取引は割に合うと判断しています。**図が多い紙面ほど、ごみを拾う割合が上がります。**

### 縦中横の直しを、横書きパスにも掛ける

縦組みの中で横に寝かせた数字（縦中横）は、1 文字分の枠に詰められているので、読み違えると必ず「1 文字」に化けます。これを数字に戻すのが `fix_tatechuyoko()` です。

以前はこれを**縦書きパスにしか掛けていませんでした。** ところが縦組みの紙面は横書きの設定でも読んでおり（どちらの読みを採るかは後で信頼度で決める）、**横書きの設定で読んでも同じように化けます。** 利用者の縦組みの資料での実測。

| 正しい数字 | 横書きパスの読み | 拾い直しの信頼度 |
|---|---|---|
| 43 | `は` | 96 |
| 56 | `%` と `ぶ` | 96 |
| 12 | `D` | 96 |

利用者が報告した `(昭和%ぶ年)` は、この `%` と `ぶ` そのものです。数字自体は `sparse_numbers()` が信頼度 96 で正しい位置に見つけているのに、**横書きパスが採用されたページでは丸ごと捨てていました。**

1 文字分の大きさの測り方だけを切り替えます（`cell_size()`）。縦組みなら列の幅、横組みなら行の高さ。これに収まらない数字は、ふつうの大きさで置かれた数字なので触りません。

**直した語の信頼度は上げません。** 横書きパスの信頼度は `pick_columns()` がそのページを縦横どちらの読みで採るかの判定に使うので、1 文字直しただけで判定が動くと、関係のない語まで入れ替わります。実測で、上げると 52/64 が 50/64 に落ち、縦組みの見開きで `1950年` と `壁量計算に加` が消えました。

### 英字に化けた日本語を、切り出して読み直す

利用者の資料で `本書は、` が `AIS,` になっていました。**紙面全体を一度に読ませたときだけ起きます。**

| 読ませ方 | 結果 | 信頼度 |
|---|---|---|
| 紙面全体（`jpn+eng` / PSM 3） | `AIS,` | 57.9 |
| その場所だけ切り出す | `本書は、` | **93** |

切り出したときは、言語データを `jpn` だけにしても `jpn+eng` のままでも、PSM を 7 / 8 / 6 / 13 のどれにしても、余白を 2 / 6 / 12 画素のどれにしても、**すべて `本書は、` の 93** でした。言語データの組み合わせの問題ではなく、**まわりの候補に引きずられること自体**が原因です。

`fix_latin_runs()` が、次をすべて満たす語だけを切り出して読み直します。

1. 漢字・かなを含まず、英字を含む語（`AIS,` のように読点が付いていても対象。数字だけの語は対象外）
2. 4 文字以内
3. 信頼度が 80 未満（正しく読めた英字は高く出る。実測で `AIS,` は 57.9、まわりの日本語は 93〜95）
4. その行に日本語が 8 文字以上ある
5. **読み直した結果が漢字・かなを含み、元より信頼度が高い**

5 が最後の砦です。`PDF` を切り出して読み直しても日本語は返らないので、元のまま残ります。

#### 枠がぴたり重なる数字は、大きさを問わない

縦中横の数字は 1 文字分の枠に収まるので、それより大きい数字は「ふつうの大きさで置かれた数字」とみなして触りません。この見積もりが**わずかに足りず**、直せる数字を見送っていました。

```
「43」信頼度96 幅34 高28  1 文字分の見積もり 27 の 1.25 倍（33.75）を超える → 見送り
     重なり1.00 「は」信頼度96 幅34 高28 字数1
```

**0.25 画素です。** しかも置き換え先の `は` は 34×28 で、数字とまったく同じ枠でした。

1 文字の語と枠がぴたり重なっているなら（両方向の重なりが 0.9 以上）、それ自体が「1 文字分に収まっている」証拠なので、大きさは問わないことにしました。ページ番号（重なる語が無い）や、ふつうの大きさの数字（1 文字とは枠が一致しない）は、これまで通り弾かれます。

実物 4 つの合計は 59/64 から **60/64**。縦組みの `43年前の基準` が取れるようになりました。

### 読み飛ばされた縦中横の数字を差し込む

縦中横は 1 文字に化けるとは限らず、**丸ごと読み飛ばされる**ことがあります。利用者の機械で変換された PDF から取り出した実物。

```
1950年(昭和年)      ← 25 が 1 文字も無い
1995年(平成年)      ← 7 が無い
2000年(平成年)      ← 12 が無い
2024月佐藤実        ← 年10 が無い
```

化けていれば置き換える相手がいますが、無ければいません。以前はここで**信頼度 96 で見つけた数字を捨てていました**。捨てていた理由は、紙面の数字を無条件に拾う読み取りなので、ノンブル（ページ番号）のような本文と関係のない数字も混ざり、列に差し込むと本文の途中にページ番号が割り込むためです。

`insert_number()` は `keep_holes()` と同じ考え方で分けます。**その行の語に前後を挟まれている数字だけを差し込みます。** ノンブルは紙面の隅に 1 つで立っているので、挟む相手がいません。

実物 4 つの合計は 54/64 から **56/64**。`2000年(平成12年)` が縦組みの 2 つとも取れるようになりました。

### 行を 1 本ずつ切り出して読み直す

`fix_latin_runs()` は語 1 つを切り出して読み直しますが、それでは足りない場合があります。利用者の資料の署名の行での実測（tesseract 5.5.3、500dpi）。

| 読ませ方 | 結果 | 信頼度 |
|---|---|---|
| 紙面全体 | `2024` …… `月佐藤実`（`年10` が消える） | 57.5 |
| その行だけ切り出す | `2024年10月佐藤実` | **92** |

消えているのが `年`（漢字）と `10`（数字）の両方なので、語 1 つを切り出しても届きません。

**行としてまとめる前に呼びます。** まとめたあとでは「2024」と「月佐藤実」の 2 つに切れてしまい（間が広く空いているので離れた語として切られる）、消えた `年10` はちょうどそのすきまにあります。tesseract が付けた行番号で束ねれば、すきまごと切り出せます。

読ませ方は **PSM 13（生の 1 行として読む）**。同じ行を 3 通りの切り出し方で読ませた実測です。

| 切り出し | PSM 7 の信頼度 | PSM 13 の信頼度 |
|---|---|---|
| A | 31 | 92 |
| B | 91 | 88 |
| C | 31 | 93 |

**返る文字はどれも `2024年10月佐藤実` で正しく、違うのは信頼度だけ**でした。採否を信頼度で決めるので、振れないほう（PSM 13）を使います。

#### すべての行を読み直す（自信の低い行だけでは足りない）

最初は「その行の信頼度が 75 未満」に絞っていました。**絞らずに全部の行を読み直すほうが良い**と実測で分かりました。

| | 合計 | 横組みの `はじめに`（以前の資料） | 4 ページの所要 |
|---|---|---|---|
| 自信の低い行だけ | 57/64 | 15/16 | 149 秒 |
| **すべての行** | **59/64** | **16/16** | 187 秒 |

**ただし、これは差し引きの数字です。** 実際に文字が変わった行は 4 資料で 6 本あり、その中身は 4 本が改善、2 本が悪化でした。

| 差し替え | 判定 |
|---|---|
| `をなくす**次**も` → `をなくす**姿**も`（2 資料） | ○ |
| `2024**月**佐藤実` → `2024**年10月**佐藤実` | ○ |
| `会話を通じて**伺味**や` → `会話を通じて**興味**や` | ○ |
| `**mm**とても大切` → `**"とてゃ**も大切` | × |
| `**や**実務の現状` → `**ゃ**実務の現状` | × |

字数でみると 8 字ほど直って 2 字壊れます。**「以前は正しかった所が壊れる」ことが実際に起きます。**

もっと安全な形（**字が増えるときだけ**差し替える＝取りこぼしの回復だけを認め、字の入れ替えは認めない）も測りました。差し替えは 1 本だけになり悪化は 0 ですが、合計は 57/64 に戻ります（`姿` と `興味` を取り逃す）。

信頼度では両者を分けられません。改善も悪化も上がり幅は 0〜2 ポイントで重なります。差し引きで良いほうを採りました。

行を丸ごと入れ替えるので、悪くしないための条件を残しています。

1. 読み直しが元より信頼度が高い
2. 読み直しが元より短くならない（字を減らさない）
3. 読み直しが漢字・かなを含む
4. 横組みの行だけ（縦組みは `fill_vertical_gaps()` の受け持ち）

なお `read_patch()` は使えません。あれは縦組みのすきま埋め用で**漢字・かなを含まない語を捨てる**ので、`2024` と `10` が消えます。`read_line()` を別に立てました。

実物 4 つの合計は 56/64 から **57/64**。`2024年10月` が取れるようになりました。

#### 縦組みの列を丸ごと読み直すのは、効かなかった

同じことを縦組みの列にもしてみました（列の枠で切り出して `jpn_vert+jpn` / PSM 5 で読み直す）。**差し引きゼロで、採りませんでした。**

| 資料 | 差し替え | 判定 |
|---|---|---|
| 縦組みの見開き | `「新耐震基準」`(83.8) → `[新耐震基準」`(91.3) | × 開きかっこが壊れる |
| 縦組みの本 | `[新耐震基準|`(86.1) → `[新耐震基準」`(87.6) | ○ 閉じかっこが直る |

**信頼度の差でも分けられません。** 悪いほうが +7.5、良いほうが +1.5 と逆でした。正解語の点数も 59/64 のまま動きません。

**「列が長すぎるから」は誤りでした。** そう書いていましたが、測ると違いました。

同じ列を、切り出す上端だけ動かして読ませた実測です（500dpi、tesseract 5.5.3）。

| 切り出し | 信頼度 | 結果 |
|---|---|---|
| 列の全体（34 字） | **0** | `」` だけ |
| 上端を 127 画素（約 2 字分）下げる | 76 | `の1981年に改正された耐震性能を「新耐震基準と呼ぶよ。` |

**2 字分ずらすだけで変わります。長さの問題ではありません。**

その列の上端には、**オレンジ地に白抜きの大きな見出し**（`★FILE 01` と誌面の題）がありました。見出しの領域を白で塗りつぶすと、同じ全体の切り出しが信頼度 87 で正しく読めます。

tesseract は切り出した画像**全体を 1 つのしきい値**で白黒にします。地の明るさが違う領域が混ざると、しきい値がそちらに引かれて本文の黒文字が潰れます。明るさの中央値の実測は、見出しの領域 156・本文 230・混ぜた全体 209 でした。

そこで「語ごとに地の明るさを見て、明るい地が続く所だけ読み直す」方式も作りました（`paper_bright()` と `reread_column_runs()`）。**壊滅的な失敗は防げますが、残りはやはり差し引きで負けます**（1 本改善・3 本悪化）。

**では短く区切ればよいか。試して駄目でした。** 列を 6 語ずつの区切りに分けて読み直すと、**1 本が改善、7 本が悪化**しました。

| 差し替え | 判定 |
|---|---|
| `柱頭接合)が` → `柱頭柱脚の接合)が` | ○ |
| `変わってきたの` → `変わっきたのっ` | × `て` が落ちる |
| `のが1981年` → `のがが1981年` | × 継ぎ目で重複 |
| `知っておくべき` → `知っておおくべき` | × 同上 |
| `「新耐震基準」と` → `一新耐震基準」レと` | × |

原因は**継ぎ目**です。区切りを語の数で機械的に決めるので、切れ目が語の途中に来ます。余白を付けて切り出すと隣の字の一部が入り、それがもう 1 文字として読まれます（`がが`・`のの`・`おお`）。逆に切れ目で字が落ちることもあります。

**横書きの行（30 字）で効いて、縦組みの列（30 字）で効かない理由は、まだ分かっていません。** 字数は同じなので、長さでは説明がつきません。地の明るさが揃った本文だけを切り出しても、元の読みと同じくらい間違えます（28 字の切り出しでも閉じかっこが落ちるのを実測）。ここが行き止まりです。

仕組みは `reread_weak_lines(..., columns=True)` と `reread_column_runs()` として残してあります（どちらも呼んでいません）。次に試す人が同じ道をたどらないためです。

### 横書きのパスでは、縦組みを探させない（いちばん効いた 2 つ目）

「切り出せば読めるのに、紙面ごとだと読めない」の**原因が 1 つ分かりました**。字が潰れているのでも、解像度が足りないのでもなく、**tesseract が読む向きを間違えている**だけでした。

見開きの紙面では、右の頁が縦組みというだけで、**左の頁にある横書きの段落まで縦組みとして読まれます**。実測（利用者の縦組みの資料 `1ca57185-____1.pdf`、500dpi、tesseract 5.5.3、`jpn+eng`/PSM 3）。

| 読ませ方 | その段落の結果 |
|---|---|
| 紙面の全体をそのまま | `改-:改=討性例人能` `1ご:法か震特性` |
| その段落だけ切り出して PSM 6 | `新耐震基準ができた3年後の1984年に「4号特例」が始まりました。` |
| 紙面の全体 + `-c textord_tabfind_vertical_text=0` | `新耐震基準ができた3年後の1984年に「4号特例」が始まりました。` |

`upright_only()` が、**横書きで読むパスにだけ**この指定を足します。縦組みは `LANG2` の縦書きパス（PSM 5）が別に読むので、横書きのパスで縦組みを探す必要はありません。縦書きのパスには足しません（足せば縦組みそのものが読めなくなります）。

効果は大きく、**その頁が丸ごと戻ります**。実測（4 つの実資料、tesseract 5.5.1）。

| 資料 | 切りなし | 縦組み判定を切る |
|---|---|---|
| 縦組み `tate.pdf` | 14/26 | **23/26** |
| 横書き `yoko.pdf` | 15/16 | 15/16 |
| 横書き `moto.pdf` | 16/16 | 16/16 |
| 縦組み `moto2.pdf` | 12/26 | **20/26** |
| 合計 | 57/84 | **74/84** |

**横書きだけの資料は 1 語も動きません。**動くのは見開きの縦組みだけです。

数え方を変えた点を明記します。**これまでの 16 語には、左の頁の語が 1 つも入っていませんでした。**そのため左の頁が丸ごと化けていても点に出ず、見落としていました。縦組みの資料には左の頁の 10 語（`4号特例`・`1984年`・`法改正ロードマップ`・`四分割法`・`見付面積`・`計算省略`・`耐震性能は向上しません`・`構造計算・検討不要と勘違い`・`平屋建て`・`令46条`）を足し、64 点満点を 84 点満点に改めました。旧来の 16 語だけで数えると 57→54 で**下がって見えます**が、それは左の頁を数えていないためです。

代償も書きます。右の頁で 3 語が落ちました（`「木造住宅の耐震性能って` の `木` が落ちる、`43年前の基準` が `43年前前の基誉` になる、`阪神淡路大震災` の `災` が落ちる）。一方で `耐力壁の配置バランス` は**逆に読めるようになりました**（長く未解決だった箇所）。差し引きで 17 語の増です。

`tools/selfcheck.py` の「読む向き」の項目が回帰テストです。tesseract は呼ばず、横書きのパスにだけ指定が付き、縦書きのパスには付かないことを引数で見ます。

#### その代償：縦組みの列の読みが 1 通りだけになる

**それまで問題の無かった箇所が、この変更で崩れます。**理由ははっきりしています。実測（利用者の縦組みの資料 `1ca57185-____1.pdf`、500dpi、`jpn+eng`/PSM 3）。

| 横書きのパス | 縦組みとして読まれた列 |
|---|---|
| 縦組み判定 あり（旧） | **68 本** |
| 縦組み判定 切る（新） | **0 本** |

旧では、縦組みの列に**2 通りの読み**（横書きパスの縦読みと、縦書きパスの縦読み）があり、`pick_columns()` が列ごとに突き合わせていました。新ではそれが 1 通りになります。横書きパスの読みのほうが良かった列は、そのぶん落ちます。

実際に、横書きパスは縦組みの列をこう読んでいました。

```
信頼度 86.7  し「木造住宅の耐震性能って
信頼度 92.9  の耐震性能へと改正されたのが1981年(昭和%ぶ年)だよ。こ
信頼度 81.7  の1981年に改正された耐震性能を[新耐震基準と呼ぶよ。
```

**3 回目の読みを足して 2 通りに戻す案は、測って否定しました。**

| 読み方 | 合計 |
|---|---|
| 3 回目 なし | 74/84 |
| 3 回目 あり（信頼度が上なら差し替え） | **74/84** |
| 3 回目 あり（8 ポイント以上の差で差し替え） | 74/84 |

差し引きゼロで、中身が入れ替わるだけでした（`moto2.pdf` で `43年前の基準` が戻る代わりに `耐力壁の配置バランス` が落ちる）。tesseract をもう 1 回呼ぶぶん**読み取りの時間が 5 割増える**のに、得るものがありません。仕組みは `prefer_columns()` として残してあります（呼んでいません）。

#### 「その場所だけを切り出せば直る」は、縦組みには当てはまらない

切り出しが効くかどうかは**場所によって逆になります**。同じ紙面の 2 本の列を、紙面ごと／その列だけで読み比べた実測です（500dpi、`jpn_vert+jpn`/PSM 5、余白 8 画素）。

| 列 | 読ませ方 | 結果 | 信頼度 |
|---|---|---|---|
| A | 紙面ごと | `…1981年に改正された耐震性能を[新耐震基準」と呼ぶよ。` | 84.7 |
| A | その列だけ | `…1981年に改正された耐震性能を[新耐震基準」と呼ぶよ。` | 86.6 |
| B | 紙面ごと | `建築基準法ができたのが1930年(昭和お年)、そこから現在` | 79.4 |
| B | その列だけ | `建築ます和合人な人基準本人生和。。法和。,がおのでと人生きた人のがを1950のききaa\|ii年(昭和02年))、そこっかP人ら人人人現和。在` | **40.4** |

**列 B は、切り出すと壊滅的に悪化します。**無い字が大量に湧きます（`人`・`和`・`生`）。字数が同じ列 A ではほとんど変わりません。

つまり「切り出せば直る」は、**横書きの段落と、たまたま条件の合う列にだけ言えること**で、縦組みの列一般には言えません。左の頁の段落が切り出しで直ったのは、そこが横書きで、しかも読む向きの判定を間違えていたからです（原因が向きだったので、向きを直せば紙面ごとでも直った）。列 B の誤りは向きの問題ではないので、切り出しても直りません。

#### 見開きを左右に切り分けても、残りの誤りは減らない

「縦書きと横書きが同じ紙面に混ざっているのが原因では」という見方は、**一度は当たっていて、いまは外れています**。

当たっていた分は、上の「縦組みを探させない」で直した左の頁です（0/10 → 10/10）。**残りは混在のせいではありません。**利用者の見開き（左が横書き、右が縦組み）を、画像の段階で左右に切り分けて別々に読ませた実測です。

| 読ませ方 | 左の頁 | 右の頁 | 合計 |
|---|---|---|---|
| 見開き 1 枚のまま | 10/10 | 13/16 | **23/26** |
| 左右に切り分けて | 9/10 | 14/16 | **23/26** |

**差し引きゼロです。**切り分けると右の頁で `「木造住宅の耐震性能って` と `43年前の基準` が戻る代わりに、左の頁で `四分割法`、右の頁で `変わってきているんだね` が落ちます。自動で左右に切る仕組みは入れません。

縦組みがまったく無い資料でも誤りは残ります（`yoko.pdf` は 15/16 で `2025年4月` が落ちる）。混在は、残っている誤りの説明になりません。

### 描き出す解像度を紙面に合わせる

`DPI` を決め打ちにすると、**貼られている画像より粗く描き出してしまう**ことがあります。本を見開きで取り込んだ資料が典型で、3042×2159 の画像が 438×311pt（＝実効 500dpi）のページに貼られているのに 300dpi で描き出すと、画像を 0.6 倍に縮めてから読むことになります。縮んだぶん小さな文字は潰れ、行ごと丸ごと落ちます。

そこで描画の前に、そのページに貼られた画像の実効解像度を調べます（pdfium で画像オブジェクトの画素数と配置範囲を取り、`72 × 画素数 ÷ 点数`）。ロゴやハンコに引きずられないよう、**ページの 40% 以上を覆う画像だけ**を見ます。`DPI` より細かければそこまで上げ、`MAXDPI`（既定 600）で頭打ちにします。下げることはしません。上げたページでは画面に「画像が細かいので 500 dpi」と出ます。

実例（本の見開き 1 ページ、`mixed`）。300dpi 固定では読めなかった語が読めるようになります。

| 語 | 300dpi 固定 | 自動（500dpi） |
|---|---|---|
| 阪神淡路大震災 | × | ○ |
| 壁量計算 | × | ○ |
| 建築基準法ができたのが | × | ○ |
| 随分古い基準だね | × | ○ |
| 倒壊した | × | ○ |

`tools/selfcheck.py` の「画像の細かさ」の項目が回帰テストです。570dpi 相当の画像を小さなページに貼った PDF を作り、300dpi 固定では落ちる語が自動では読めることを見ます。

### 色の付いた文字と、白黒への落とし方

**OCR にかける前にページを白黒にするのはやめました。** 白黒のほうが速く画像も軽いのですが、**色の付いた帯の上に白抜きで組んだ見出しが読めなくなります。**

利用者の紙面で実際に起きたのがこれです。オレンジの帯に白抜きで組んだ「本書の構成とねらい」が、`SAS ORE BDU)` に化けていました。原因は明るさの差です。

| 見方 | 帯 | 白い文字 | 差 |
|---|---|---|---|
| 輝度（白黒に落とす） | 154 | 254 | **100** |
| 青の板だけで見る | 65 | 255 | **190** |

オレンジは青がほとんど無いので、色のまま渡せば差は倍近くあります。白黒に落とした時点で、その差は捨てられます。

同じ紙面を最後まで通して数えた結果です。狙った語のうちいくつ取り出せたか。

| 紙面 | 白黒に落とす | 色のまま |
|---|---|---|
| 横組み二段（見開き） | 7/16 | **10/16** |
| 縦組みの本（見開き） | 13/16 | **15/16** |

どちらの紙面でも色のままが多く、白黒でしか取れなかった語はありませんでした。戻った語は「本書の構成とねらい」「地盤調査業者」「構造検討や構造計算」「昭和25年」「平成12年」。利用者の環境と同じ 5.5 系でも、`改正できるよう、mult記載しています` の `mult` が消え、`地調査業者` が `地盤調査業者` に戻りました。

`ink_image()`（R/G/B のうち最も暗い値で白黒にする）は、白黒に落とすことを前提に色付きのインクを救う処理でした。色をそのまま渡すほうが成績がよかったので、既定では使いません。`設定.ini` の `GRAYSCALE=yes` に戻したときのために残してあります。

ページ数が多くて時間やメモリが足りないときだけ `GRAYSCALE=yes` にしてください。

`tools/selfcheck.py` の「白抜き」の項目が回帰テストです。ただし**化けること自体は合成した紙面では安定して再現できませんでした**。字の大きさと JPEG の圧縮を振って探すと、再現する条件は紙一重で、同じ設定のまま色のほうが落ちることもありました。そこでこの項目は「化けないこと」を測らず、**判断の理由のほうを固定します**。色を捨てていないこと、輝度より青の板の差が大きいこと、色のまま渡しても見出しと本文が読めること、の 3 つです。

### 縦横が混ざったページ

tesseract は 1 回の読み取りで縦組みと横組みを同時には扱えません。横書きの設定では縦組みの列が 1 文字ずつばらばらの読み違いになり、縦書きの設定では横組みが崩れます。

`mixed` モードは同じページを 2 回読みます（縦中横の拾い直しを含めると 3 回）。1 回目は `jpn+eng` / PSM 3、2 回目は `jpn_vert+jpn` / PSM 5。2 回目で**縦長に読めた日本語の行だけ**を採用し、その場所と 50% 以上重なっていた 1 回目の結果は捨てます（捨てないと同じ場所に二重の文字が残ります）。読み取りが 2 回になるので、時間はおよそ倍かかります。

`設定.ini` の `[mixed]` にある `LANG2` / `PSM2` が 2 回目の設定です。`LANG2` を空にすれば 1 回だけの読み取りに戻ります。他のモードでも `LANG2` を書けば 2 回読みになります。

差し替えの細かい規則は次のとおりです。

- **縦組みとみなすのは 2 文字以上つながった日本語の列だけ**。横書きの行を縦書きの設定で読むと 1 文字ずつばらばらの「列」になるため、これを弾く
- **同じ場所を横書きが自信を持って読めているなら、縦組みとは認めない**（下記）
- ただし**同じ列の続きに見える 1 文字は拾う**。列は途中に横向きの数字が入ると分断され、残りが 1 文字（「…できたのが 1950 年、」の「年」）になるため
- **縦中横（縦組みの中の横向きの数字）は横書きパスから拾い直す**。縦書き用の言語データは横向きの数字を読めない。列と重なっていても、数字で、まだ出ていないものなら残し、列の並びに混ぜる
- 拾い直すのは**数字だけ**。英字は絵を文字と読み違えたもの（`POUCHES` のような）なので捨てる
- ページ全体が縦組みなら、列の外で拾った英字（イラストの模様）も捨てる

置く順番は、コピーしたときに並ぶ順番になるビューア（pdfium 系）があるため、読む順に並べ替えます。縦組みは**同じ縦線上のかたまりにまとめてから右の列**、横組みは上の行から。

#### 縦中横（縦組みの中の横向きの数字）

縦組みでは、二桁までの算用数字を横に寝かせて 1 文字分の枠に詰めます（縦中横）。縦書き用の言語データはこの組み方を読めず、**必ず別の 1 文字に化けます**。実際の資料では `(昭和25年)` → `(昭和お年)`、`(昭和56年)` → `(昭和ぶ年)`、`(平成12年)` → `(平成に年)` となりました。横書きの設定で読ませても、ページ全体では周りの縦組みに引きずられて同じように化けます。

そこで、縦書きで読む設定のときだけ、`-l eng --psm 11`（文字が散在）で**数字だけを拾う 3 回目の読み取り**を足します。PSM 11 は行の並びを推測しないので、縦組みに埋もれた数字のかたまりを素直に拾えます。上の 3 か所はいずれも信頼度 94〜97 で読めました。拾うのは信頼度 80 以上・二桁以上・縦より横に長いものだけです。

拾った数字は、**行としてまとめる前に**縦書き側の結果へ差し込みます。あとから足すのではなく元の位置で置き換えるので、コピーしたときの並びが崩れません。置き換え先は次のように決めます。

- 化けるのは 1 文字なので、**1 文字の語だけ**が候補
- 数字の枠と**重なっている**ものを選ぶ。「いちばん近いもの」で選ぶと、数字が読み飛ばされているときに隣の正しい文字を消してしまう
- 数字が**列の幅からはみ出していれば置き換えない**。縦中横は 1 文字分の枠に収まるので、はみ出すものは普通の大きさで置かれた数字であり、化けた文字は存在しない。tesseract が返す 1 語ごとの枠は上下左右に膨らんでいて当てにならないため、同じ列にある語の幅の**中央値**を列の幅として使う
- 置き換え先が無かった数字は**捨てる**。紙面の数字を無条件に拾う読み取りなので、ノンブル（ページ番号）のような本文と関係のない数字も混ざる。これを列に差し込むと、本文の途中にページ番号が割り込む（一度そうしてしまった）。縦組みに置かれた普通の大きさの数字は、もともと横書きのパスから拾い直す仕組みがあるので、そちらに任せる

#### 縦に積まれた数字

三桁以上の数字（西暦など）は縦中横にできないので、縦組みでは **1 文字ずつ縦に積んで**組みます。縦書き用の言語データはこれを 1 つの語として読もうとして外します。実物では `1950` を**信頼度 24 で「1930」**と読み、`MINCONF` の下限に届かず数字ごと消えていました（コピーすると「建築基準法ができたのが 年(…」）。

まとめて読ませると外しますが、**1 文字ずつ切り出して読ませれば当たります**。

- 切れ目は、その列の**インクの途切れ**で決める。枠を字数で等分すると外れる。tesseract が返す枠は数字の後ろに続く「年」まで含んでいるため（`1950` の枠は 4 文字ぶんではなく 5 文字ぶんあった）
- 切り出した 1 文字は、まわりに余白を足して正方形にしてから拡大する。ぎりぎりに切り出したままだと `1` と `0` を読み落とす（実測で 4 桁中 2 桁）
- 1 文字だけを読ませると数字が形の似た英字に化けるので（`1`→`l` `]`、`0`→`O`）、読み替え表で戻す
- 数字でない字が出たらそこで止める。後ろの「年」を巻き込まない
- 元の字数と一致したときだけ差し替える
- 読み直せなかった低信頼度のものは捨てる。誤った数字を残すと検索で誤って当たる

**信頼度で読み直す・読み直さないを決めてはいけません。** はじめは「信頼度 85 以上は当たっているはずなので触らない」としていました。これが最大の落とし穴でした。同じ画像の同じ誤読が、tesseract 5.3.4 では**信頼度 24**、5.5.x では**信頼度 87** で返ります。開発環境（5.3.4）では常に読み直されて直り、利用環境（5.5.x）では 85 の壁に阻まれて素通りする——**手元では直っているのに、相手の環境では何も変わらない**という状態が続きました。いまは信頼度に関わらず読み直し、代わりに**1 文字ずつの読みそれぞれに下限（60）**を課します。採否の根拠を「tesseract の自己申告」から「読み直した結果そのもの」へ移すのが要点です。

#### 列の途中で落ちた字を拾い直す

紙面に出ていて、まわりの字は取れているのに、**1〜2 字だけ候補としても現れない**ことがあります。実物では `(昭和25年)` の「昭和」が丸ごと消えました。信頼度が低いのではなく、TSV に行として存在しません。下限を下げても出てきません。

そこで、**同じ列で上下に並ぶ語の間隔**を見ます。1 文字分以上あいていれば、そこを列の幅で切り出してもう一度だけ読ませます。切り出すと候補が絞られるので、まわりに引きずられずに読めます（実測で「昭和」を**信頼度 90**、「そこ」を 88、「年」を 56 で回収）。

**空振りしたときに何を返すかが問題でした。** 何も無い所を読ませても tesseract は空を返しません。小さな断片を、自信を持って返します（実測で `局` を信頼度 81、`震` を 92）。信頼度では捨てられません。

決め手は次の 2 つで、**どちらか一方では足りません**。

- **すきまが 2 文字分以上あること。** tesseract が返す枠はインクにぴったり沿っているので、字と字の間には常にすきまがあります。1 文字分を境にすると、詰まって並んだ所まで読みに行って無い字を作ります。落ちた 1 文字は、その上下のすきまと合わせて 2 文字分以上の穴になります
- **読めた字が、そのすきまを 35% 以上埋めること。** 穴の大きさに見合う字が返ってきたときだけ採ります

実測値です。○が本物、×が空振りです。

| すきま/字 | 埋まり | 読めたもの | |
|---|---|---|---|
| 2.17 | 0.84 | `昭和`（信頼度 90） | ○ |
| 2.47 | 0.39 | `年`（56） | ○ |
| 2.72 | 0.94 | `そこ`（88） | ○ |
| 2.82 | 0.28 | `震`（92） | × |
| 2.65 | 0.18 | `局`（81） | × |
| 1.25 | 0.80 | `へ`（50） | × |
| 1.34 | 0.59 | `の`（95） | × |

しきい値を「すきま 1.1 文字分」だけにしていたとき、5.3.4 では 6 か所すべてが誤りで、`(昭和56年)` が `(昭和56へ年年)` に悪化しました。2 つを揃えると、5.3.4 で誤り 0 件、5.5.1 で正しい 3 件・誤り 0 件になります。

補助的な条件が 2 つあります。

- **その行の字の大きさが、紙面全体の中央値の 0.5〜2 倍に収まること。** 図や罫線の切れ端も「行」としてまとまります。実物ではそこに 155px・242px のすきまがあり、読ませると `計` `量` `壁` `地` `柱` といった断片が本文に紛れ込みました
- **読めた字が漢字・かなであること。** 記号の切れ端（`|` `】`）を落とす

上下の相手が漢字・かなであることは**条件にしません**。まさに直したい `(昭和25年)` が、かっこと数字に挟まれているためです。

`tools/selfcheck.py` の「すきま拾い」の項目が回帰テストです。`(昭和25年)から` と組んだ列から「昭和」だけを抜いた状態を作り、拾い直せること、かつ詰まっている所を読みに行かないことを見ます。

そのために、縦書きのパスでは**積まれた数字だけ拾う下限を下げて**おきます（`MINCONF` で捨てられる前に確保する）。

`tools/selfcheck.py` の「積んだ数字」の項目が回帰テストです。`2 0 2 4 年` と積んだ画像を作り、`2024` が読めて「年」を巻き込まないことを見ます。

#### 本物の列と、縦書きの読み違いを見分ける

縦書きの設定は、紙面のどこを読ませても縦組みとして読みます。横組みの本文も、イラストも、罫線でさえ、それらしい漢字の列に化けます。長さ・形・信頼度のどれを見ても本物と区別がつきません（実際、化けた列のほうが信頼度が高いことがよくあります）。

決め手は**同じ場所を横書きで読んだ結果と比べること**です。重なった面積で重みを付けた信頼度を計算し、

- 横書きが**その場所を読めている**（列の 20% 以上を覆っている）なら、信頼度の高いほうを採る。横書きが勝つ場所はもともと横組みか、そもそも文字ではない
- 横書きが**何も読んでいない**場所は比べようがないので、縦書き側の信頼度が 75 以上のものだけ残す

**わずかな差で勝たせてはいけません。** 横組みの本文を縦に読み違えた列は、信頼度が本物の横書きとほとんど並びます（実測で 94.5 対 93.5）。1 ポイントの差で縦組みと認めると、そこへ 1 文字の読み違いが芋づる式にぶら下がり（実測で 9 本の偽の列）、重なっていた正しい横書きまで消えます。**8 ポイント以上の差**を求めます。

さらに**紙面全体での割合**も見ます。ほとんどが横組みの紙面に残ったわずかな「列」は、まず読み違いです。列が担う漢字・かなの数が、横書きのそれの 8% に満たなければ、列は 1 本も採りません。実測値は、横書きだけの紙面 4.6%・見出しだけ縦組み 16.1%・縦組みの本 104.6% で、はっきり分かれました。

縦組みを先に置くか後に置くか（＝コピーしたときの順）も、この割合で決めます。当初は「横書きより多いか」でしたが、縦組みの本の実測が 0.98 でわずかに届かず、本文より図表が先に来る順になりました。いまは**半分**を境にします（0.98 と 0.16 のどちらからも遠い）。

実際の見開きページでは、本物の縦組み（信頼度 75〜94）に重なる横書きの信頼度は 40〜60 にとどまり、イラストを読み違えた列（信頼度 85〜96）に重なる横書きは 83〜96 でした。この 1 本の規則で、混ざり込んでいた読み違いがほぼ消え、あわせて**それまで読み違いに潰されていた横書きの本文が復活します**（読み違いと重なった横書きは捨てられていたため）。

1 文字の拾い直しは、この選別を通った列に対してだけ行います。順序を逆にすると、読み違いの列に 1 文字ずつぶら下がって傷口が広がります。

### 二段組み・見開きの読む順

横組みを「上から下へ、同じ高さなら左から右へ」だけで並べると、二段組みや見開きのページで**左の段の 1 行目・右の段の 1 行目・左の段の 2 行目…**と交互になります。コピーすると文章が互い違いになって読めません。

```
本書は、木造住宅の「構造」について解説をしています。  ②構造のセミナーを受講しても理解できない、③構造を
木造住宅に「なぜ、構造？」と思われるかもしれません。  身近にいないという方は、筆者が行っている「構造塾」を
```

**tesseract の段組みの判定は当てにできません。** 同じ紙面でも、描き出す解像度が違うだけで結果が変わりました。

| 描き出す解像度 | tesseract の block |
|---|---|
| 150dpi | 左右を別の block に分ける（正しい） |
| 300dpi | 1 つの block にまとめ、1 行が左右にまたがる |

そこで段の切れ目はこちらで探します。**紙面のどの高さにも文字が無い縦の帯**が段の切れ目です。全ての語の x 範囲を x 軸に投影し、覆われずに残った幅が「1 行の高さ × 1.5」と「紙面の幅 × 2%」のどちらよりも広ければ、そこで割ります。行と行のすき間や文の途中の空白は、他の行がその位置を覆うので残りません。

段が見つかったら **(段, 上端, 左端)** の順に並べます。ただし上端の値をそのまま使うと、同じ行でも枠が数ピクセルずれるために語順が入れ替わります（`木造住宅に「なぜ、` `と思われるかもしれません。` `構造`）。行の高さの 0.6 倍以内に収まるものを 1 行にまとめてから、行の中を左から右へ並べます。

切れ目の片側に語がほとんど無いときは、段ではなく余白やノンブルなので割りません。縦組みは右の列から読むのでこの並べ替えは当てはまらず、`sort_columns` が受け持ちます。

`tools/selfcheck.py` の「二段組み」の項目が回帰テストです。左右に 5 行ずつ置いたページを作り、左の段を読み切ってから右の段に移ること、行の中の語順が保たれることを見ます。

### 行にくっついたイラストを落とす

縦組みの列の上や下にイラストがあると、その模様が `St` `KHOY` のような英字に読まれ、tesseract は**それを本文と同じ行として返します**。害は 2 つあります。

1. コピーすると本文の先頭に余計な字が混じる
2. **行の枠がイラストまで広がり、透明な文字が本物より上にずれて置かれる**

2 のほうが厄介でした。行の枠に合わせて文字を割り付けるので、枠が上に伸びた分、先頭の何文字かが紙面の文字より上に描かれます。紙面を見ながら選択しても、その数文字だけ拾えません。実物では「木造住宅の…」の見出しが 10pt 上にずれ、`「木` の 2 文字が選択から漏れていました。

縦に組まれた日本語の中に英単語が縦向きに現れることはまずないので、**縦組みの行の端にある英字だけの断片を落とします**。間に挟まったものは型番などの可能性があるので残します。落とすと枠も縮むので、ずれも直ります。

`tools/selfcheck.py` の「イラスト」の項目が回帰テストです。OCR を通さず、行をまとめる処理に `St / 木 / 造 / KHOY` を直接渡して、`木造` だけが残り、枠が本文の位置に縮むことを見ます。

### 向きの扱い

| 場面 | 対応 |
|---|---|
| ページに `/Rotate` が付いている | pdfium が表示どおりに描画するので、重ねるときに座標を回転前の系へ戻す |
| 紙が横倒し・上下逆でスキャンされている | `tesseract --psm 0`（OSD）で向きを判定し、画像を立て直して読み、枠を元の座標へ戻す |
| 縦書き | 縦長の枠に入った日本語は「上から下へ読む文字」として、90 度回した見えない文字を置く |

### ページが内容を共有している PDF

スキャナが作る PDF では、全ページが同じ内容ストリーム（画像を 1 枚貼るだけの短い命令列）を**1 つのオブジェクトとして共有**していることがあります。pypdf は重ねた結果を元と同じオブジェクトに書き戻すため、共有されたままだと 1 ページに重ねた文字が全ページに現れ、しかも各ページのフォント対応表で解釈されるので文字化けします。重ねる前に `/Contents` の参照を調べ、共有しているページには自分専用の複製を持たせています。

`tools/selfcheck.py` の「内容共有」の項目がこの回帰テストです。漏れた文字は化けて語では見つからないため、ページごとの字数が膨らんでいないかで判定します（共有なし `[121, 89]` に対し、修正を外すと `[210, 207]`）。

### すでにテキスト層がある PDF

昔の OCR ソフトが付けたテキスト層が入っている PDF は、そのまま重ねると文字が二重になり、検索も選択も乱れます（元の層の位置と内容が当てにならないため）。`--retext` は重ねる前に、その層を content stream から取り除きます。

消すのは**見えない文字だけ**です。content stream を走査してテキスト表示モード（`Tr`）を `q`/`Q` とともに追跡し、モードが 3 か 7（描画しない）のあいだの文字表示命令だけを落とします。ワープロで作った本文のような見える文字は残るので、ハイブリッドな PDF に使っても紙面は変わりません。位置がずれないよう、`'` は `T*`、`"` は `Tw`/`Tc`/`T*` に置き換えます。

走査はページの content stream だけでは足りません。ページを抜き出すソフトの出力には、**紙面まるごとが Form XObject に包まれ**、ページ側は `q /Xf1 Do Q` の 3 命令だけ、というものがあります。この場合ページの content stream には文字が 1 つもないので、消したつもりでテキスト層がそのまま残り、入れ直すと二重になります。`/Resources` の `/XObject` を入れ子までたどって、Form の中の見えない文字も落とします。書き戻すときは元の Form を書き換えず、中身を入れ替えた複製を作ってページ側の参照だけを差し替えます（他のページが同じ Form を指していることがあるため）。

`tools/selfcheck.py` の「入れ直し」の項目が回帰テストです。変換済みの PDF をまるごと Form に包み直してから `--retext` をかけ、字数が倍にならないことを見ます（修正を外すと `[121, 89]` が `[242, 178]` になります）。

### 速度

tesseract は内部でも複数スレッドを使うため、そのまま同時実行すると CPU の取り合いで**かえって数十倍遅くなります**。複数ページを並列で読むときは `OMP_THREAD_LIMIT=1` を渡して、1 プロセス 1 スレッドにしています（3 ページの例で 96 秒 → 2.7 秒）。

大判の図面（A1・A0）を 300dpi で描画すると画像が 1 億画素を超えるため、`MAXPIXELS` を上限に解像度を自動で落とします。

**1 枚あたりの内訳**（実物 1 ページ、500dpi、tesseract 5.5.3、この開発機で実測）。

| | `tate.pdf`（縦横混在） | `yoko.pdf`（横組み） |
|---|---|---|
| 変換ぜんぶ | **58.9 秒** | **61.9 秒** |
| うち 横書きパス 1 回（`jpn+eng` PSM 3） | 13.8 秒 | 13.8 秒 |
| うち 縦書きパス 1 回（`jpn_vert+jpn` PSM 5） | 8.1 秒 | 8.1 秒 |
| うち その他（数字の拾い直し・弱い行の読み直し・描画・重ね合わせ） | 約 37 秒 | 約 40 秒 |

**読み取り 2 回で 22 秒、残りの 37 秒は後処理**です。複数ページは並列で読むので、実際の待ち時間はページ数に比例しません。

## 設定

`設定.ini`（メモ帳で編集可）で既定値を変えられます。`[settings]` が共通、`[auto]` `[yoko]` `[tate]` `[mixed]` `[zumen]` `[eng]` が読み取り方ごとの上書きです。

| 項目 | 意味 |
|---|---|
| `DPI` | ページを画像にする解像度（既定 300。小さい文字が読めないときだけ 400） |
| `MAXDPI` | 貼られた画像のほうが細かいときに、そこまで上げてよい上限（既定 600。`0` で `DPI` に固定） |
| `GRAYSCALE` | 白黒にしてから読むか（既定 yes。色付きの帯や蛍光ペンの上の文字を取りこぼすときは no） |
| `NUMBERS` | 縦組みの中の横向きの数字（縦中横）を拾い直すか（既定 yes。縦書きを含む読み取りのときだけ働く） |
| `MINCONF` | 採用する信頼度の下限（既定 30。下げると拾う文字が増え、誤読も増える） |
| `SUFFIX` | 出力名に付ける文字（既定 `_OCR`） |
| `SKIPTEXTPAGES` | すでに文字が入っているページを飛ばすか |
| `TEXTPAGECHARS` | 何字以上で「文字入りのページ」と見なすか（既定 100。ページ番号やハンコだけの薄いテキスト層で飛ばされるのを防ぐ） |
| `AUTOROTATE` | 横倒し・上下逆のページを自動で立て直すか |
| `MAXPIXELS` | 1 ページの画像の画素数の上限 |
| `JOBS` | 同時に読むページ数（0 で自動） |
| `TESSERACT` / `FONT` / `OUTDIR` | 実行ファイル・フォント・出力先の指定 |
| `MODE` | 読み取り方の既定（`auto` / `yoko` / `tate` / `mixed` / `zumen` / `eng`。既定 `auto`） |
| `LANG` / `PSM` | tesseract の言語データとページ分割モード |
| `SPARSEPSM` / `SPARSEUNDER` | `auto` で、文字列がこの数に満たないページを読み直すときの分割モードとしきい値 |

図面で文字を取りこぼすときは `[zumen]` の `PSM` を 11 → 12 → 6 と試してみてください。

## 開発者向けの検証

### この README の「◯◯/64」とは

**4 つの資料 × 16 個の語 = 64 点**の抜き取り検査です。文字の正解率ではありません。

**4 つの資料**

| | 中身 | 出どころ |
|---|---|---|
| `tate.pdf` | 縦組みの見開き 1 頁 | 利用者が送ってくれた実物 |
| `yoko.pdf` | 横組み二段の 1 頁 | 利用者が送ってくれた実物 |
| `moto2.pdf` | `tate.pdf` と**同じ紙面** | こちらで別に描き直したもの |
| `moto.pdf` | `yoko.pdf` と**同じ紙面** | こちらで別に描き直したもの |

同じ紙面を 2 通りの描き出しで入れてあるのは、**片方の描き出しでしか効かない直しを見破るため**です（実際に、拡大して読む案は `yoko.pdf` で `2025年4月` が直る代わりに `moto.pdf` で壊れました）。

**16 個の語**

紙面から先に決めておいた正解の語です。縦組みの 2 つと横組みの 2 つで別の一覧を使います。

```
縦組み   新耐震基準 / 昭和25年 / 2000年(平成12年) / 耐力壁の配置バランス /
         43年前の基準 / 「木造住宅の耐震性能って / 随分古い基準だね …
横組み   構造塾 / 2025年4月 / 意欲をなくす姿 / ぜひともご活用ください /
         経験と勘で「構造」 / 予測されている震災による被害 …
```

**数え方**

変換後の PDF から取り出した文字を全部つなげ、空白を除き、全角半角を NFKC でそろえます。その中にその語が**そのままの並びで**入っていれば 1 点。

**この物差しの弱点 その 1：行またぎ**

語が行またぎで切れていると、**字が全部合っていても 0 点**になります。PaddleOCR を測ったときに実際に起きました（`震災による倒` と `壊被害` が別の行に出るので、`震災による倒壊被害` は取れない）。字の単位で見たいときは、縦組み 4 列 116 字との一致数を別に数えています。

**この物差しの弱点 その 2：縦組みは、目に見えない入れ直しで 4 点動く**

同じ紙面を JPEG で入れ直しただけの写しを 6 通り作って採点しました。画素の差は最大でも 8〜9（256 段階）、**目では区別できません。**

| 縦組み（`tate.pdf` とその写し） | 点 | | 横組み（`yoko.pdf` とその写し） | 点 |
|---|---|---|---|---|
| 元 | **13**/16 | | 元 | 15/16 |
| 入れ直し（`moto2.pdf`） | **10**/16 | | 入れ直し（`moto.pdf`） | **16**/16 |
| 品質 98 | **10**/16 | | 品質 98 | **16**/16 |
| 品質 95 | **13**/16 | | 品質 95 | **16**/16 |
| 品質 92 | **9**/16 | | 品質 92 | **16**/16 |
| 品質 88 | **13**/16 | | 品質 88 | **16**/16 |
| **幅** | **9〜13（4 点）** | | **幅** | **15〜16（1 点）** |

**揺れているのは縦組みだけです。**横組みは 1 点しか動かず、その 1 点も既知の `2025年4月` です。

縦組みは品質の順にも並びません（98→10、95→13、92→9、88→13）。規則性が無い＝ただの揺れです。欠ける語の顔ぶれも毎回変わります。元で取れている `1995年(平成7年)` が品質 98 では欠け、元で欠けている `昭和25年` が品質 95 では取れます。

**原因は認識器です。**`tate.pdf` と `moto2.pdf` の読みを、後処理に入る前の `parse_vertical` の時点で並べると、差はそこで既に付いています。

```
tate    …1930年(昭和お年)…   …随分古い基準だね…   …壁量計算に加千え、壁の配置…
moto2   …1930年(咽和お年)…   …陸分古い基準だね…   …壁量計算に  千え、  の配置…
```

`昭`→`咽`、`随`→`陸`、`加` と `壁` の脱落。後段の `fix_tatechuyoko` 以降はどれも字を減らしていません。

**この README を読むときの目安**

- **縦組みが絡む ±1〜2 点の差は、根拠として弱い。**揺れの範囲に入ります。
- **横組みで測った差は、そのまま信頼できます。**
- **3 点以上の差、または字の単位で示した差は残ります**（`upright_only` の +17、単語表を抜くと −6、PaddleOCR mobile 42 対 server 48 など）。

この揺れは 2026-08-30 に初めて測りました。**それ以前に書いた ±1 点の比較は、この目安で読み直してください。**

#### 物差しを直した（字を袋で数える）

2026-08-30、上の揺れを受けて物差しを作り直しました。案は 2 つありました（「字の単位で数える」「縦組みの資料を増やす」）。手元に新しい縦組みの実物が無いため、**前者を選びました**。

**やり方**

1. 紙面を見て正解の文章を全部書き起こす。縦組みは `tate.pdf` 右頁の対話文 4 コマぶん（460 字）、横組みは `yoko.pdf` 1 頁の地の文（1,297 字）。見出し・ページ番号は含めない
2. 正解の文字を「袋」（順序を問わず、字種ごとの個数だけを数える入れ物）に入れる。変換後の文字も同じ袋に入れ、正解の袋にある字が変換後の袋にも同じ個数以上あれば、その字は一致とみなす
3. 一致した延べ字数 ÷ 正解の文字数、が点数

16 語の合否と違う点が 2 つあります。

- **順序を問わない。** 弱点その 1「行またぎ」（字が合っているのに行が割れて 0 点になる）が起きない
- **標本が大きい。** 460 字・1,297 字を丸ごと数えるので、1 字の誤りが点数に与える影響が 16 分の 1 から数百分の 1 に薄まる

**汚染源を断つ。** `tate.pdf` は見開き 1 枚の PDF で、左頁（図版）にも同じ年号（1984 年・1995 年・2000 年など）が出てきます。紙面全体をそのまま突き合わせると、左頁の字を右頁の正解と誤って一致させてしまいます。そこで**右頁だけを切り出してから測ります**。実際の変換結果を変えるものではなく、測定だけの処置です（自動で左右に切る仕組みは入れていません。上の「見開きを左右に切り分けても、残りの誤りは減らない」を参照）。

**揺れは縮んだが、消えてはいない。** 同じ 6 通りの入れ直しを、新しい物差しで測り直しました（いまのツール）。

| | 旧物差し（16 語） | 新物差し（字の袋、縦 460 字／横 1,297 字） |
|---|---|---|
| 元 tate.pdf / yoko.pdf | 13/16・15/16 | 縦 94.8%・横 99.5% |
| 入れ直し moto2.pdf / moto.pdf | 10/16・16/16 | 縦 94.8%・横 99.6% |
| 品質 98 | 10/16・16/16 | 縦 97.0%・横 99.6% |
| 品質 95 | 13/16・16/16 | 縦 95.7%・横 99.6% |
| 品質 92 | 9/16・16/16 | 縦 87.4%・横 99.6% |
| 品質 88 | 13/16・16/16 | 縦 96.1%・横 99.6% |
| **縦組みの幅** | **9〜13（4 点＝揺れ幅 25%）** | **87.4〜97.0%（揺れ幅 9.6 ポイント）** |
| **横組みの幅** | **15〜16（1 点＝揺れ幅 6.3%）** | **99.5〜99.6%（揺れ幅 0.1 ポイント）** |

割合で見た縦組みの揺れは 25% から 9.6 ポイントに縮みました。標本を大きくした効果は出ています。**ただし消えてはいません。** 横組みの揺れは 0.1 ポイントまで縮んだのに対し、縦組みだけ依然として大きく揺れます。原因は前と同じで、認識器そのもの（`parse_vertical` の時点）が JPEG の入れ直しで読みを変えるためです（`昭`→`咽`、`随`→`陸`、`加`と`壁`の脱落など）。

### 利用環境と同じ版の tesseract で確かめる

このツールで一番手こずったのは、**開発環境と利用環境で tesseract の版が違う**ことでした。同じ画像・同じ設定でも、返る文字と信頼度が版によって変わります。実例：

| | 5.3.4（開発環境） | 5.5.x（利用環境） |
|---|---|---|
| 縦に積まれた `1950` | `1930` を信頼度 **24** で返す | `1930` を信頼度 **87** で返す |
| `(昭和25年)` の「昭和」 | `和` だけ読む | 2 字とも読まない |

信頼度で分岐している所は、これで挙動がまるごと変わります。「信頼度 85 以上は触らない」という規則を入れていたため、開発環境では毎回読み直されて直り、利用環境では素通りしていました。**手元の検証はすべて通るのに、相手の環境では何も変わらない**という状態が数回続き、当て推量で直そうとして時間を費やしました。

打開したのは、**利用環境と同じ版を同じ機械に用意する**ことです。`tesserocr` の wheel は tesseract 本体を同梱しているので、apt の版と別の版を並べて動かせます。

```
pip install tesserocr
python3 tools/repro.py 対象.pdf --keyword 昭和25年 --keyword 1950年
```

`tools/repro.py` は `pdf_ocr.run_tesseract` だけを差し替え、それ以外は本番と同じ道を通します。これで利用環境の症状がそのまま再現でき、当て推量が普通のデバッグに変わりました。**版によって挙動が変わる部品に依存するときは、まず相手の版を手元に用意する**ことです。

利用者側から見分けられるように、実行時に画面の先頭へ版（`PDF文字認識 版 2026.08.28`）を出し、調査ファイルにも書き込みます。「直したはずのものが直っていない」ときに、古いファイルが動いているのか、直し方が悪いのかを、その場で切り分けるためです。

#### 利用者と同じ版そのものを作る

`tesserocr` の wheel が同梱するのは 5.5.1 で、apt は 5.3.4。利用者の 5.5.3 はどちらでもありません。**ソースから作れます。**

```sh
apt-get install -y --no-install-recommends libleptonica-dev
git clone --depth 1 --branch 5.5.3 https://github.com/tesseract-ocr/tesseract
cmake -S tesseract -B build -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_INSTALL_PREFIX=$PWD/t553 -DBUILD_TRAINING_TOOLS=OFF
cmake --build build -j"$(nproc)" && cmake --install build
LD_LIBRARY_PATH=$PWD/t553/lib $PWD/t553/bin/tesseract --version
```

`pdf_ocr.ocr_pdf()` は tesseract の道筋を引数で受け取るので、これを渡せば本番と同じ道を通せます（`repro.py` の差し替えより素直）。**「版が違うから直せない」と書く前に、その版を作ってください。**

### 「何度やり直しても結果が変わらない」を作らない

もう 1 つ、同じ誤解を生んでいた原因がありました。**bat が `--overwrite` を渡していませんでした。**

`output_path()` は、出力先が既にあると `_OCR_2.pdf` `_OCR_3.pdf` … と別名に逃がします。上書きしない安全策のつもりでしたが、bat の案内文には「変換後は 元の名前_OCR.pdf として同じ場所に保存されます」と書いてあり、**ツール自身の説明と食い違っていました**。2 回目以降の実行はすべて別名で保存され、利用者が最初に開いた `_OCR.pdf` はいつまでも初回のままです。何度直して送っても「結果が変わらない」と見えます。

出力は元の PDF から作り直せるもので、残す価値はありません。bat は `--overwrite` を渡すようにし、あわせて**保存先の絶対パスと更新時刻**を実行のたびに表示します。

### 調査ファイルは、最終結果まで含める

`--dumpocr` は当初、縦書きのパスの結果だけを書き出していました。ところが実際にコピーされる文字は、横書きのパスと縦書きのパスを突き合わせて決まります。そのため調査ファイルと利用者の手元のコピー結果が食い違い、**同じ機械の同じ実行なのに別物に見えて**、原因を読み違えました（調査ファイルの `しぎ「林造` に対し、コピー結果は `「木造`。前者は縦書きのパス、後者は横書きのパスが採用された結果で、どちらも正しい）。

いまは `[4] 横書きで読んだ結果` と `[5] 最終的に PDF に入る文字` まで書き出します。**利用者に見えているものと同じものが、控えにも載っている**ことが要点です。

### 試して駄目だったこと

1 文字だけ自信を持って誤読される場合（利用者の資料で `新耐震基準` が `新耐謀基準` になった。同種の再現例として `意欲をなくす姿` が `次` になる）について、2 通り試してどちらも駄目でした。

**その 1：同じ文書に何度も出る語で直す。** そのファイルの中に正しい `新耐震基準` が 6 回あります。「1 回しか出ない語が、3 回以上出る同じ長さの語と 1 文字だけ違うなら直す」という規則を、利用者の変換後 PDF 2 つで机上に試しました（漢字かなだけ・4 文字以上に絞ってなお）。**54 件の直しを提案し、正しいのは 1 件だけ**でした。

| 提案 | 判定 |
|---|---|
| `新耐謀基準` → `新耐震基準` | ○ 狙い通り |
| `木造住宅は` → `木造住宅の` | × 単語ですらない切れ端 |
| `理解できる` → `理解できな` | × 意味が壊れる |
| `建築基準法が` → `建築基準法改` | × 壊れる |

**ただし、この失敗の原因は規則の作りが雑だったことです。** 文章から 5 文字の窓を機械的に切り出して比べたので、`木造住宅は` のような単語ですらない切れ端が候補に紛れました。**「日本語だから無理」ではありません。** 単語の切り出しを持てば結果は変わりえます（辞書を持ち込む話になるので、この道具では採りません）。

### 別の認識器（PaddleOCR / PP-OCRv5）を実測した

「PaddleOCR のほうが日本語（縦書き・横書き）に強い」と聞く。**同じ 4 資料・同じ 16 語・同じ 500dpi の画像で測りました。**

**mobile（小さいほう）と server（大きいほう）の両方**を測りました。server の模型は、この環境から模型置き場に届かないので、利用者に落としてもらって `ppocr_server/` 経由で受け取ったものです（`PP-OCRv5_server_det_infer.tar` 88,340,480 バイト／`PP-OCRv5_server_rec_infer.tar` 84,869,120 バイト）。

|---|---|---|---|---|---|---|
| PP-OCRv5 **mobile**（1 回呼ぶだけ） | 11 | 11 | 8 | 12 | 42/64 | 約 6.8 秒 |
| PP-OCRv5 **server**（1 回呼ぶだけ） | **13** | 11 | 11 | **13** | 48/64 | 約 41 秒 |

| いまのツール（tesseract ＋ 作り込み） | 13 | **15** | **16** | 10 | **54/64** | — |

#### 縦と横に分けると、話がはっきりします

#### server で残った 3 語は、原因が 3 つとも違う

縦組みの 2 資料で server が落とした語は、`1995年(平成7年)`・`耐力壁の配置バランス`・`2000年(平成12年)` の 3 つだけです。中身を見ると：

| 落とした語 | 実際の出力 | 原因 |
|---|---|---|
| `耐力壁の配置バランス` | `耐力壁の配` … `置バランス` が離れて出る | **列の順番**。PaddleOCR は縦組みの列を並べ替えない |
| `1995年(平成7年)` | `1995年平成7年の` | **括弧が落ちる** |
| `2000年(平成12年)` | `2000年(平成1年)` | **縦中横**。横に寝かせた 2 桁が 1 桁になる |

3 つ目は、このツールが `sparse_numbers()` と `fix_tatechuyoko()` で既に解いている問題そのものです。1 つ目も `sort_reading_order()` と `pick_columns()` が解いています。**PaddleOCR に足りないのは字を読む力ではなく、その後の組み立てでした。**

#### 横組みの `yoko.pdf` で mobile と server の点が同じ（11／11）なのも、組み立てのせい

落とした 5 語は mobile と server でまったく同じで、中身を見ると**どれも行またぎで切れている**だけです。

```
mobile  …震災による倒 / 木造住宅にとって…      ← 「壊被害」が別の行に行っている
server  …震災による倒 / 木造住宅にとって…      ← 同じ
mobile  …経験と勘で「構 / 造を考えてきた…
server  …経験と勘で「構 / 気軽に相談できる…
```

二段組みの左右の行が交互に出てくるので、行をまたぐ語が繋がりません。**字は読めています。**同じ場所で server は `盛り込ました`（mobile）を `盛り込みました` と正しく読み、`「構造は` を `「構造」は` と閉じています。**点が動かないのは、読めていないからではなく、並べられていないからです。**

**縦書きに強いのは本当でした。**縦組みの `tate.pdf` では、素の PP-OCRv5 が素の tesseract を上回ります（11 対 9）。縦組みの列を「縦長の枠」として 22 本見つけ、確信度 0.95〜0.99 で読みます。向きの指定は要りません。

```
枠 54x951 conf=0.99  え壁の配置バランス柱頭柱脚の接合方法が耐震の基準に追
枠 61x955 conf=0.95  要であることがわかり2000年（平成12年）に壁量計算に加
```

**横書きで落ちる原因は「小さい字」です。**`yoko.pdf` 1 枚で数えました。

| | 全体 | 長音符 `ー` | かぎ括弧 `「」` | 小さいかな | 句読点 `、。` |
|---|---|---|---|---|---|
| tesseract（配布版） | 1,431 字 | **6** | 36 | 8 | 68 |
| PP-OCRv5 mobile | 1,392 字 | **0** | 27 | 6 | 68 |
| PP-OCRv5 server | 1,392 字 | 3 | 35 | 5 | 66 |

mobile の実際の出力：`セミナ一`（`ー` が `一`）・`クリト造`（コンクリート）・`プ口セス`（`ロ` が `口`）・`変わてきている`（`って` の `っ`）・`盛り込ました`（`み` が落ちる）・`もちん`（`ろ` が落ちる）。**検索できる PDF を作る道具としては、これは効きます。**「コンクリート」で引いて当たりません。

**server にすると、かぎ括弧はほぼ戻り（27 → 35）、長音符も一部戻ります（0 → 3）。**ただし tesseract の 6 には届きません。server では代わりに、`风压力`・`建築基准法`・`柱の下侧` のように**簡体字が混じる**ことがあります（多言語の模型なので）。

利用者が毎回貼っている縦組み 4 列（116 字）。

| | 4 行 116 字のうち一致 |
|---|---|
| いまのツール | **114 字（98.3%）** |
| PP-OCRv5 server | 109 字（94.0%） |
| PP-OCRv5 mobile | 102 字（87.9%） |

mobile では `昭和25年`→`昭和23年`、`43年前`→`3年前`、`「」` が消える。**server ではこの 3 つとも正しく出ます。**

**作れるかどうかは「作れる」。**配り方まで含めた実測。

| | 大きさ | 備考 |
|---|---|---|
| `paddlepaddle`（本家） | Windows wheel 99.9 MB / **入れると 721 MB** | 模型は初回に外部から取得 |
| `onnxruntime` | Windows wheel **13.4 MB** | 模型 21 MB を同梱できる |
| PP-OCRv5 **mobile** の模型 | det 4.6 MB ＋ rec 15.9 MB ＋ cls 0.6 MB = **21 MB** | 同梱できる |
| PP-OCRv5 **server** の模型 | det 84.2 MB ＋ rec 80.9 MB = **165 MB** | いまの ZIP が 13.2 MB。**同梱できない** |

ONNX 版なら、**Tesseract のインストーラが丸ごと不要になります**（`使い方.txt` でいちばん厄介な「Additional language data のチェック」が消える）。準備は `pip install onnxruntime` の 1 行が増えるだけです。

**採らない理由**（2026-08-29 時点）。

1. **そのまま置き換えると落ちる。**mobile は 54/64 → 42/64。server でも 48/64 で届かず、しかも**同梱できない大きさ**（165 MB）で、1 枚 41 秒かかる。
2. **PaddleOCR は行単位の枠しか返さない**（tesseract は単語単位）。見えない文字の位置は行の枠に均等割りすることになり、いまより粗くなる。
3. **同梱するなら模型のライセンスを自分で確かめる必要がある。** 測るのに使った `onnxocr` は PyPI にライセンス表記が無い。PaddleOCR 本家は Apache-2.0 なので、本家の模型を自分で ONNX に変換すれば筋は通る。

**捨てていない道**：縦組みでは **server が 26/32 対 23/32 でこのツールを上回りました**。いまの「横書きパス＋縦書きパス」の**縦書き側だけを PP-OCRv5 にする**のは、これで根拠のある案になりました。しかも server が落とした 3 語のうち 2 語（列の順番・縦中横）は、このツールが既に持っている後処理で直せるものです。ただし 165 MB を配れないので、**やるなら mobile で同じ差が出るかを先に確かめる必要があります**（mobile の縦 2 つは 23/32 で、いまのツールと同じ）。まだやっていません。

#### 「配れるのは mobile だけ」の理由は、大きさ 1 点だけ

理由になりそうなものを 3 つ潰しました。**残ったのは大きさだけです。**

**① 枠組みの 721 MB → 理由になりません。**server の模型は Paddle 形式ですが、`paddle2onnx` で ONNX に変換できます。実測（`paddle2onnx` 2.1.0）。

**② ライセンス → 理由になりません。訂正します。**前に「同梱するなら模型のライセンスを自分で確かめる必要がある」と書きましたが、**それは `onnxocr` という非公式の再配布物についての話**でした。今回の server は PaddleOCR 公式の配布元から直接落としたもので、PaddleOCR は Apache-2.0 です。同梱してかまいません。

**③ 大きさ → これだけが残ります。**

#### `paddlepaddle` と `onnxruntime` は、別の OCR ではない

上の 2 行は**同じ網（ニューラルネット）を動かす、2 通りの動かし方**です。精度の話ではありません。

| | 正体 | できること | 大きさ |
|---|---|---|---|
| `paddlepaddle` | 深層学習の**枠組み** | 網を作る・訓練する・動かす | Windows wheel 99.9 MB／入れると 721 MB |
| `onnxruntime` | 訓練済みの網を**動かすだけ**の実行系 | 動かすだけ | Windows wheel 13.4 MB |

**同じ網であることの裏取り。** 使った ONNX ファイルの中身を見ると、節点の名前に `p2o.` が入っています（`det` 1,010 個・`rec` 957 個・`cls` 563 個）。`p2o` は PaddlePaddle 自身の変換道具 `paddle2onnx` の印です。**入れ物を変えただけで、重みは同じ数値です。**

**721 MB の中身**（入れたものを実測）。

```
266 MB  paddle/base/libpaddle.so            枠組みの本体（自動微分・訓練）
130 MB  paddle/libs/libmklml_intel.so       Intel の数学ライブラリ
118 MB  paddle/libs/libphi_core.so          演算子の実装一式
 64 MB  paddle/libs/libdnnl.so.3
 63 MB  paddle/libs/libopenvino_intel_cpu_plugin.so
```

**この中に OCR の模型は 1 つも入っていません。**模型は別に落としてくる 21 MB です。つまり 721 MB は訓練用の道具立てで、字を読む段では使いません。**本家だから精度が良い、ということはありません。**

#### 精度を変えるのは「枠組み」ではなく「模型の大きさ」

大きさの実測。mobile は ONNX ファイルから重みの数まで数えました。

| | 重みの数 | 大きさ |
|---|---|---|
| mobile det（文字の場所を探す） | 1,171,745 | 4.60 MB |
| mobile rec（文字を読む） | 4,113,256 | 15.86 MB |
| mobile cls（180 度回転を直す） | — | 0.56 MB |
| **server det** | — | **84.2 MB**（18 倍） |
| **server rec** | — | **80.9 MB**（5 倍） |

PaddleOCR には同じ PP-OCRv5 の **server（大きいほう）**もあります。この環境から模型置き場に届かないので、**利用者に落としてもらって受け取り、実測しました**（結果は上の表）。

見込みは当たっていました。**落としている字は、模型が出せない字ではありません。** 字表（18,383 字）を調べると `ー`・`っ`・`ゃ`・`ゅ`・`ょ`・`「`・`」`・`、`・`。` はすべて入っています。**出せないのではなく、出していない。**server にすると、かぎ括弧は 27 → 35、長音符は 0 → 3 に戻り、64 語の点も 42 → 48 に上がりました。**模型の大きさの問題だった**わけです。

#### 測り方（`tools/paddle_try.py`）

`tools/paddle_try.py` が、その物差しです。認識器そのものを測る道具で、本体の作り込みは通りません。

```
# 小さいほう（模型は onnxocr に同梱。この環境でも動く）
pip install onnxocr
python tools/paddle_try.py 資料.pdf --keyword 新耐震基準 --keyword 昭和25年

# 大きいほう（PaddleOCR 本体が要る。初回に模型を落としてくる）

# 大きいほう（模型を手元に置いてある場合。この環境ではこちら）
PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=False PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True \
python tools/paddle_try.py 資料.pdf --size server --no-cls \
    --det-dir 展開先/PP-OCRv5_server_det_infer \

```

`--size server` は `PP-OCRv5_server_det` と `PP-OCRv5_server_rec` を指定します（`paddleocr` 3.7.0 の `text_detection_model_name` / `text_recognition_model_name`）。模型の取得先は `huggingface.co`・`modelscope.cn`・`aistudio.baidu.com`・`paddle-model-ecology.bj.bcebos.com` の 4 つで、いずれかに繋がれば落ちてきます。

**実際に動かすまでに 4 か所で止まりました。**同じことをする人のために残します。

| 止まり方 | 直し方 |
|---|---|
| `Model name mismatch: expected 'PP-OCRv6_medium_det'` | 置き場だけでなく**模型の名前も一緒に渡す**。PaddleOCR 3.7 の既定は PP-OCRv6 |
| `PP-LCNet_x1_0_textline_ori` を落とそうとして止まる | 上下逆を直す模型だけは `--rec-dir` で渡せない。`--no-cls` を付ける |

| `Fail to alloc memory of 34292367360 size` | 場所探しの前に紙面を縮める。PaddleOCR 本体の既定は「短辺 64・上限 4000」＝実質そのままなので、server の模型が 34 GB 確保しようとする。`--det-side 960 --det-limit max`（onnxocr の既定と同じ） |

**この開発環境からは取得先が 4 つとも塞がっているので、模型は利用者に落としてもらいました。**繋がる先を探した記録（いずれも空振り）。

| `hf-mirror.com`・`gitee.com`・`gitcode.com`・`bj.bcebos.com` | 4 つとも塞がっている |

繋がる機械で落とすなら、直接の場所はここです。

```
https://paddle-model-ecology.bj.bcebos.com/paddlex/official_inference_model/paddle3.0.0/PP-OCRv5_server_det_infer.tar
https://paddle-model-ecology.bj.bcebos.com/paddlex/official_inference_model/paddle3.0.0/PP-OCRv5_server_rec_infer.tar
```

展開して `--det-dir` と `--rec-dir` で渡せば、取得先に繋がらない機械でも読ませられます（`PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` を付ける）。

**その 2：自信の低い 1 文字を切り出して読み直す。** 意味を解釈せず、字だけを見る方法。手で試した限りでは有望でした。

| 読ませ方 | 結果 | 信頼度 |
|---|---|---|
| 紙面全体 | `次`（誤り） | 70.8 |
| その 1 文字だけ | **`姿`（正しい）** | 87.5 |

ところが実物 4 つに組み込んで測ると **57/64 が 53/64 に落ちました**。差し替えた 45 文字の中身。

| 差し替え | 判定 |
|---|---|
| `震`(67) → `災`(75) | × |
| `塾`(0) → `り`(76) | × `keep_holes` で直した字を壊す |
| `盤`(0) → `を`(8) | × |
| `柱`(62) → `の`(96) | × |
| `名`(33) → `違`(85) | × |

**信頼度の上がり幅では正誤を分けられません**（`塾`→`り` は +76 も上がって誤り）。密に並んだ本文から 1 文字だけ切り出すと、**隣の字のインクが枠に入り込み**、その断片を別の字として自信を持って読みます。手で試した `姿` は、たまたま切り出しがうまくいっただけでした。

行や語のまとまりを切り出す `reread_weak_lines()` / `fix_latin_runs()` が効くのは、**切れ目が字の間ではなく、語や行の間にある**からです。1 文字はその条件を満たしません。


**英語の言語データを外す。** 日本語の本文が `本書は、` → `AIS，` のように英字へ化けるので、`LANG` から `eng` を外して `jpn` だけにしてみました。実測で **51/64 が 48/64 に落ちました**（実物 4 つ、正解語 16 個ずつ）。落ちたのは縦組みの見開きで、`建築基準法ができたのが1950年`・`昭和25年`・`壁量計算に加` が消えました。`eng` は数字と記号の読みに効いています。`LANG=jpn+eng` のままにします。

同じ紙面に何度も戻ることになるので、**測ってから捨てた案**を残しておきます。

**解像度を 2 つ使って突き合わせる。** 落ちる字は解像度ごとに違います。実測（横組み二段、狙った 11 語）で、300dpi は 8、500dpi は 4、800dpi は 8。取れる語の中身も違うので、2 つ読んで良いほうを採れば 9 まで届く計算になります。しかし**信頼度は正しさの目安になりませんでした**。

```
低い解像度  信頼度 88.2   本書は、2023年4月の…   ← 年号が誤り
高い解像度  信頼度 86.6   本書は、2025年4月の…   ← 正しい
```

信頼度で選ぶと、年号が書き換わります。字が 1 つ落ちるより悪い。行の切れ目も解像度ごとに違うので、行どうしを対応させること自体が安定しません。採りませんでした。

なお解像度そのものは、いまの決め方（画像に合わせて上げる）が最良です。色のまま渡したうえで下げてみると、縦組みの本が 15/16 から 10/16 に落ちました。

**横書きの行でも、すきまから字を拾い直す。** 縦組み向けの `fill_vertical_gaps()` と同じことを横に対して書き、実際に動かしました。すきまの信号自体ははっきり出ます（1 文字分を単位に、ふつうの字間が 0.53〜1.32 に対し、`経験と ┊ 「構` が 2.75、`震 ┊ による` が 1.77）。

ところが**切り出して読み直すと、目的の字が返りません**。tesseract の枠はインクに沿うので、落ちた字は前後の枠に半分食い込んでいて、すきまだけを切ると半分しか入りません。前後にはみ出して切り、白い余白を足し、2〜4 倍に拡大し、PSM も 6/7/8/13 を試しましたが、`勘` は `甚` に化け、`災` は何も返しませんでした。一方で**取りこぼしではない所**（`ビルダー・`、`工事業者`）は信頼度 90 超で字を返すので、入れると重複と誤字が増えます。

縦で効いて横で効かないのは、縦組みでは列という細い帯が決まっていて、1 文字を切り出せば孤立した 1 文字になるからです。横書きにその手掛かりはありません。採りませんでした。

### 未解決：縦書きパスで正しく直した数字が、列ごと捨てられる

`fix_tatechuyoko()` は縦書きパスの化けた 1 文字を数字に正しく置き換えます。ところが `combine_passes()` が呼ぶ `pick_columns()` が、その列を**横書きパスの読み違い**と誤認して丸ごと捨てることがあります。

`pick_columns()` は、縦書きパスの単語が横書きパスの信頼度を「8 ポイント以上」上回らないと採りません（横組みの本文を縦書きとして誤読した「偽の列」を弾くために、実測して決めた値）。ところが横書きパスが同じ場所を僅差で読み違えていると、**「偽の列」と「本物だが横書きパスも僅差で読み違えた列」は信頼度の差だけでは区別できません。** 弾く側に倒れているため、正しく直した数字ごと消えます。合成テストでは 94.5 対 93.3 の 1.2 ポイント差でした。

**以前ここに「合成テストだけの問題で、実物には影響しない」と書いていました。それは誤りでした。** 実物の縦組みでも起きており、`43年前の基準` がこれで消えていました。

margin を緩める案は実測して否定されました（実物 4 つ、正解語 16 個ずつ）。

| margin | 合計 |
|---|---|
| 8（現状） | 52/64 |
| 4 | 48/64 |
| 2 | 47/64 |
| 0 | 47/64 |

緩めると、縦書きパスの質の低い列まで採ってしまい、失うほうが多くなります。**この値は据え置きます。**

実物のほうは別の道で直りました。同じ縦中横の直しを横書きパスにも掛けると（`fix_tatechuyoko(..., upright=False)`）、どちらのパスが採用されても数字が残ります。合成テストの「縦中横」の項目は NG のままです。

### 未解決：回転を指定したページで、透明文字がずれる

`/Rotate` が付いた PDF で、向きの自動判定（OSD）が働くと、透明文字が写っている文字からずれます。同梱のサンプルを 90 / 180 / 270 度に回した PDF で、文字が黒い画素の上に乗っている割合。

| ページの回転 | 割合 |
|---|---|
| 0 度 | 100% |
| 90 度 | 0% |
| 180 度 | 0% |
| 270 度 | 24% |

**語はすべて取り出せます。** 崩れるのは選択したときの範囲だけです。数値は言語データの版や実行のたびに動きます（91〜94 ページで測って 0〜100 / 0〜79 / 22〜79 % の幅で出ました）。

この表の値は `keep_holes()` を入れる前後で 1 桁も変わりませんでした（変更前の `pdf_ocr.py` を `git show HEAD:` で取り出して並べて測定）。**回転のずれは、この変更とは無関係の、以前からの問題です。**

分かっていること。

- `unrotate_boxes()` は正しい（単体で確かめた。1000×600 を 90 度回した画像の左上 (0,0,100,50) は、元画像の (0,500,50,100) に戻る）。
- `--no-autorotate` を付けると 0 / 90 度は 100% に戻るが、180 / 270 度は**語が 1 つも読めなくなる**。つまり回転そのものは要る。
- OSD の答えは 3 つとも `(360 − ページの回転) % 360` で一貫している。信頼度は 4.68 / 5.72 / 5.29 で、正しいものと誤ったものを分けられない。
- 言語データの版で結果が変わる（標準版では 100%、精度重視版・速度優先版では上の値）。理由は未特定。

残っているのは、ページ自身の `/Rotate` と OSD が見つけた回転を、`overlay_matrix()` で重ねるところだと見ています。ここは直せていません。**回転を指定していない PDF（スキャナ出力の大半）では起きません。**

**2026-08-30 時点の判断（下記の再検証より前）。**縦書きの読み取りを 3 通りから選べる形にする、と決めていました。

| 選べる形 | 縦書き側 | 模型の配り方 |
|---|---|---|
| 既定 | tesseract（いまのまま） | — |
| 任意 | PP-OCRv5 **mobile** | 21 MB。**ZIP に同梱する** |
| 任意 | PP-OCRv5 **server** | 165 MB。**リリース資産に置く**（利用者の判断でお決めいただいた） |

根拠は「server が縦組みで 26/32 対 23/32 で勝る」でしたが、これは当時から「16 語の物差しは縦組みで 9〜13 に揺れる」という留保付きでした。

**測り方を直した結果、この根拠は崩れました。**（`### 物差しを直した（字を袋で数える）` を参照）字の単位（縦組み 460 字）で測り直すと、3 つの読み方の差は最大 3.4 ポイント（92.4〜95.8%）で、同じ紙面の入れ直しだけで 9.6 ポイント動きます。**差が揺れの中に収まっており、server が勝るとも、いまのツールが勝るとも言えません。** 一方、横書きは 3 通りとも tesseract が確実に勝ります（差 2.2 ポイント、揺れ 0.1 ポイント）。

**したがって、いまの手持ちの実物（縦組み 2 資料）だけでは、3 パターン選択式を作る精度上の根拠がありません。** 考えられる進み方は次のどれかです。

1. **作らない。** 精度で勝るという測定結果が無いまま、165 MB の配布・152 秒への延び・見えない文字の位置が粗くなる代償だけを払うことになる。いまの tesseract 一本のままにする。
2. **縦組みの実物をもっと集めてから決める。** 揺れ幅（9.6 ポイント）の外に出る差があるかどうかは、資料が 2 つでは判別できない。実物が増えれば分かる可能性がある。
3. **精度以外の理由で作る。** 例えば「同じ紙面の入れ直しに強い」（`tate.pdf`/`moto2.pdf` の 2 例で server の点が動かなかった。ただし 2 例だけで、しかも新しい物差しでは未確認）のような、別の観点を主目的にするなら、精度の同点は妨げにならない。

利用者の判断：**精度の同点よりも、選べること自体を優先し、作ることにしました。** 横書き・縦書きそれぞれで `tesseract` / `PP-OCRv5 mobile` / `PP-OCRv5 server` を選べる GUI を作ります。

### 実機で見つかった不具合を直す（2026-08-30）

実機の Windows で GUI を動かしたところ、2 つの不具合が見つかりました。

1. **「この画面へのドラッグ＆ドロップは使えません」と出る。**
2. **PP-OCRv5 server の模型を取得したあと、`No module named 'pyclipper'` で変換が失敗する。** ログには残るが、次に何をすればよいか分からず、フリーズしたように見える。

**原因は 1 つ、`PDF文字認識.bat` の `[8]` (GUI起動) 側にありました。** `[1] 準備` は `py -3`（見つからなければ `python`）で部品を入れますが、GUI 起動側は `where pythonw` で**別に**探していたため、Python が複数入っている機械（`py` ランチャーと Anaconda 等が両方入っている場合など）では、準備で部品を入れた Python と、実際に GUI を開く Python が食い違うことがありました。`tkinterdnd2` や `pyclipper` は後者に入っていないため、ドラッグ＆ドロップが使えず、PP-OCRv5 も動かせない、という 2 つの症状が同時に出ます（`[1]`〜`[7]` はもともと `%PY%` 一本で動くため、この食い違いは起きません）。

**直したこと 3 つ。**

1. `PDF文字認識.bat` の `:gui` を、`where pythonw` の独立探索ではなく、`[1] 準備` と同じ `%PY%` から辿る形に直した（`py -3` なら対になる `pyw -3`、`python` ならその `python.exe` と同じ場所の `pythonw.exe`。見つからなければコンソール付きでも `%PY%` で確実に開く）。
2. `pdf_ocr.py` の `get_ppocr_engine()` に、模型を取りに行く前の確認を追加した。`cv2`・`onnxruntime`・`pyclipper`・`shapely` が入っていなければ、165MB を取得して 1 ページ目で失敗させる前に、「不足: pyclipper」のように何が足りないかを名指しして `tesseract` に切り替える。一度足りないと分かったら、同じ起動中は再確認・再取得をしない（複数 PDF を続けて変換しても、同じ確認ダイアログや失敗を繰り返さない）。
3. `PDF文字認識_GUI.pyw` に、選んだエンジンが用意できず `tesseract` に切り替わったことをログへ 1 回だけ出す仕組みを追加した（`※ 横書きの読み取り: …`）。今までは静かに切り替わるだけで、選んだはずのエンジンで読まれなかったことに気づけなかった。

**確かめたこと。** 上記の (2)(3) は、`pyclipper` 等が無い状態を作って（別の Python で実際に再現）、複数 PDF を続けて変換し、1 件目でだけ理由付きのログが出て `tesseract` に切り替わり、2 件目以降は再確認なしで最後まで完了してボタンが正しく戻ることを確認しました。(1) の `:gui` のバッチ本体は、この検証環境に Windows が無いため、目で見た実行では確認できていません（コマンドプロンプトの構文として妥当であることは確認済み）。

#### 続報：ドラッグ＆ドロップは、別の原因で直っていなかった

上の直し方を実機で試したところ、`pyclipper` の失敗（フリーズに見えていたもの）は直りました。**しかし「ドラッグ＆ドロップが使えません」は、直った Python（`[1] 準備` と同じもの）でもなお出ていました。** これは Python の食い違いとは別の原因で、`tkinterdnd2` 自体・または Tcl 側の `tkdnd` 拡張の読み込みが、その機械でそもそも失敗している、ということです。

原因の切り分けに使えるコードの穴も 1 つ見つけました。`tkinterdnd2`（PyPI の現行版）は、`tkdnd` 拡張を読み込めないとき `tkinter.TclError` ではなく `RuntimeError` を投げ直す実装になっています。ところが `PDF文字認識_GUI.pyw` の `main()` は `except tk.TclError:` でしか受けていなかったため、この版の `tkinterdnd2` が入っている機械では、ドラッグ＆ドロップが使えないどころか **GUI が起動時に落ちて何も出ない**、という一段階ひどい壊れ方をしうる状態でした（今回はまだ起動できているので、この経路そのものではなさそうですが、直さないままにする理由はありません）。

**直したこと。**

1. `main()` の `TkinterDnD.Tk()` と、`_build_ui()` の `drop_target_register()` を、どちらも `Exception` 全般で受けるように広げた（版によって `TclError` のことも `RuntimeError` のこともあるため）。これでどちらが失敗しても、画面自体は必ず開き、ボタンでの選択に切り替わる。
2. **失敗した理由をそのまま画面に出す**ようにした。「この画面へのドラッグ＆ドロップは使えません」の下に、`（原因: drop_target_register() 失敗（TclError: …））` のように、実際の例外の種類とメッセージを 1 行添える。原因を推測で潰そうとするより、次に実機で見えた文言をそのまま教えてもらう方が早いと判断した。

**確かめたこと。** `TkinterDnD.Tk()` が `RuntimeError` で失敗する場合・`drop_target_register()` が `TclError` で失敗する場合の両方を作って、どちらも画面が落ちずに理由付きのラベルへ切り替わることを確認しました。実機での本当の原因（`tkinterdnd2` が入っていない／`tkdnd` の同梱バイナリがその Windows の構成〈32/64bit・ARM 等〉に合わない、など）は、次に出る「原因: …」の文言待ちです。

#### 続報：原因は「単純に入っていなかった」

画面に出た文言は `tkinterdnd2 が無い（No module named 'tkinterdnd2'）` でした。`pyclipper` 等（同じ `pip install` の並びにある）は動いている Python なのに、`tkinterdnd2` だけ入っていない、という状態です。`[1] 準備` を今すぐ実機でやり直してもらい、そのとき pip が何を言うかを見るのが最短ですが、それを毎回頼むのではなく、**`[1] 準備` の最後に、この 2 つ（画面のドラッグ＆ドロップ・PP-OCRv5）が実際に使えるかどうかを、その場で名指しして出す**ようにしました。今までは `--selftest` が tesseract 側しか見ておらず、GUI 専用の部品が足りないことは GUI を開くまで分かりませんでした。

- `pdf_ocr.py --selftest`（`[1] 準備` の `[3/3]` から自動で呼ばれる）に、`画面のドラッグ＆ドロップ: OK / 入っていません（理由）` と `PP-OCRv5（縦書き・横書きで選べる読み取り）: OK / 入っていません（不足: …）` の 2 行を追加した。
- 「入っていません」のときにコピーしてそのまま実行できるよう、入れ直す pip コマンド（`tkinterdnd2 onnxruntime opencv-python-headless pyclipper shapely` をまとめて `--upgrade`）を `[1] 準備` の最後に案内として出すようにした。

これで、次に `[1] 準備` をやり直してもらえば、画面を開かなくても「何が足りないか」がその場で分かります。

### GUI変換ログを追加し、tesseract に「速度重視版」を選べるようにする

GUIのログ欄は閉じると消え、完了時刻・所要秒数も出ていなかったため、変換ログ（CSV）を追加した（前項）のに続けて、「今の tesseract は精度重視版だが、速度重視版のオプションを付けられるか」という質問があった。

**現状の設計は逆方向だった。** `upgrade_langs()` は「速度優先版（`tessdata_fast`）が入っていたら精度重視版（`tessdata_best`）へ自動で入れ替える」という、速度優先版を積極的に避ける作りになっている。実測（本 README 記載）では、同じ紙面 1 ページで `tessdata_fast` が 2.4 MB・16〜34 秒・狙った16語中9〜15/16、`tessdata_best`（今の既定）が 14.3 MB・46〜52 秒・15/16。横書きはおよそ3〜4割速くなるが、紙面によっては明確に精度が落ちる。縦書き用の `jpn_vert` は両版でほぼ同じ大きさで差が無いと分かっている。

利用者の判断：**横書き・縦書き両方のプルダウンに `tesseract（速度重視）` を追加する**（縦書き側は効果が薄いことを承知のうえで、操作の一貫性を優先）。

**実装。**

- `pdf_ocr/src/tessdata_fast/jpn.traineddata`（`tessdata_fast` 版、2.4 MB）を新たに同梱した。`tessdata/jpn.traineddata`（精度重視版）と同じく、tesseract 公式配布（Apache-2.0）から取得している。
- `eng`・`jpn_vert`・`osd` は精度重視版と速度優先版で差が無いと分かっているため、速度優先版でも同じファイルをそのまま複製して使う（`ensure_fast_tessdata()`）。新たに落とすのは `jpn` の 2.4 MB だけ。
- `ocr_image()` の横書き・縦書きそれぞれのパスで使う `tessdata` の置き場を、`ENGINE1`/`ENGINE2` が `tesseract_fast` かどうかで独立に切り替えるようにした（`tessdata1`/`tessdata2`）。片方だけ速度重視、もう片方は精度重視、という組み合わせも選べる。
- 精度重視版が「自信が無い」ときに元の版で読み直す既存のしくみ（`_TESSDATA_ALT` による in_doubt 再読）は、`tesseract`（精度重視・既定）を両方選んでいるときだけ働く。速度重視版を明示的に選んだパスでは、二重に読み直す無駄を避けるため働かない。
- GUI（`PDF文字認識_GUI.pyw`）のプルダウンに `tesseract（速度重視・小さい言語データ）` を追加した。用意できなければ（同梱ファイルが欠けている等）精度重視版に静かに戻し、既存の「※ …」ログでその旨を知らせる。

**確かめたこと。** 実際に `tesseract_fast` を選んで変換し、同梱の `jpn.traineddata`（速度重視版）が正しく使われること、横書き・縦書きを別々に選べること、同梱ファイルを欠けさせた状態でも精度重視版へ落ちて完了することを確認した。手元の実測では同じページで精度重視版 62.9 秒に対し速度重視版 27.3 秒（文字数はほぼ同じ）と、確かに速くなることも確認した。
